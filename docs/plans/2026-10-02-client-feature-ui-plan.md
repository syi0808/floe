## Concrete caller and owner risks

1. **Calendar Action composition:** `FloeApp` accepts a separate `calendarActions` value but does not use it. `PersonalDayScreen` has no such constructor input, and `initState` creates its action controller only when the Day gateway also implements `CalendarActionGateway`. Use the specified explicit ActionsGateway injection through FloeApp and PersonalDayScreen, migrating every caller together. Do not preserve the hidden multi-interface assumption with a forwarding shim.
2. **Connection navigation:** `AgentInteractionCard._actionButton` handles `openConnection` through an optional callback then refreshes; every `AgentPanel` construction in `PersonalDayScreen._content` and `_openAssistant` omits `onOpenConnections`. Hook the actual owning connection surface during the interaction cutover. `requestPermission` currently only refreshes and needs owner-specific review rather than implied permission.
3. **Obsolete authority contract:** `AgentInteractionKind.processingRecipient`, `recipient_consent`, `AgentConsentScope` and `AgentRecipientConsentTarget` carry concrete recipient/profile/source scopes. The card renders those fields, AgentPanel maps `consent_required`, Data/privacy hardcodes exact-recipient approval, and remote-server Settings describes per-request sensitive approval. Migrate these callers with the canonical source-processing owner; preserve source identity, digest/revision review binding, decisions and Run observation. Pairing cannot become source or Action permission.
4. **Dart part boundaries:** Five PersonalDay parts and three Settings parts share one library's imports/private symbols. `_openNote` in tasks.dart calls `_NoteDetail` in notes.dart. Import-only deletion searches miss these edges; part declarations and owning libraries must move atomically.
5. **Knowledge placement:** `knowledge/presentation/agent_memory_review.dart` contains pure candidate/review DTOs, decision enum and gateway, with no widgets. The chosen domain/application split migrates all runtime/controller/settings imports; old test references have the T0 disposition rather than a compatibility export; no compatibility re-export should remain.
6. **Source/cache/action separation:** CalendarPanel configures Connections source then syncs Day; PersonalDayScreen joins source with mirror, refreshes and collects exact action results. Observer/UI lifetime cannot silently cancel backend work, and uncertain writes must lead to lookup/collection rather than duplicate direct mutations.
7. **Static UI follow-ups:** Calendar axis handles 23/25-hour days but guides paint 48 half-hours; hardcoded English/old no-edit copy remains; preview task subtasks and suggestions are local UI state, not persisted backend objects. These observations are not an invitation to expand the refactor into unrelated visual changes.
