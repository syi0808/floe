## Repository methods and atomic semantics

All signatures are in `ports/repository.rs`, boxed Send futures and typed values. SQL is the physical boundary; no policy callbacks and no provider/native I/O inside transactions.

- `get`, `list`: the one encrypted authority. Stable bounded pagination by Action UUID, strictly after cursor, limits 1–100. Do not merge another list. Validate all loaded rows/indexes. Return `next_cursor` only if more records exist.
- `find_admission`: inspect the exact Person/command receipt first. Same submit command and exact `request_digest` returns the current associated ActionRecord; changed digest or a command reused for another kind conflicts. It must not revalidate current policy, source, Task availability or expiry for replay.
- `admit`: transaction checks command replay first, then calls `validate_action_admission(admission, current_authority)`, validates Expert Task/grant evidence as described below, inserts ActionRecord and command receipt atomically. Exact concurrent replay joins the same record. `AdmittedAction.replayed` reports whether the receipt already existed.

  Manual Action/Execution/Review IDs derive from the direct command UUID with separate domains. Expert IDs derive from a domain-separated digest of Person plus the complete immutable TaskExecutionReceiptRef plus artifact UUID, then separate Action/Execution/Review domains, as enforced by `ActionOrigin::identity_seed` and `ActionRecord::validate`. Unrelated Task receipts that happen to contain the same artifact UUID cannot masquerade as replay. A new command colliding with a retained Expert Action ID must Conflict unless that same command's exact receipt already exists; it never starts a second effect from an already used proposal.
- `record_decision`: transaction receipt first using `decision_intent_digest`, which excludes observation time `now` but includes command, actor Person/device, Action, expected revision, immutable review reference and decision. Exact retry returns the current authoritative associated record before fresh expiry/policy checks. Otherwise invoke `decide_action(record, decision, authority)` and atomically persist new record plus receipt. Approval is never inferred from a boolean outside this owner command.
- `admit_reconciliation`: receipt first, exact full `ActionReconciliation` identity (Person/device/Action/expected revision); changed intent conflicts. New admission requires exact current revision and Executing/Unknown/collection-pending state, then records the command without dispatch or invented evidence. A terminal result on an exact earlier command replay still returns its current authoritative record. This is lookup-only owner workflow admission.
- `stop_before_dispatch`: invoke `stop_action`; it can only move pending/approved work with no immutable ExecutionIntent into explicit predispatch Blocked/Expired/Cancelled. Never use it after handoff or discard an uncertain record.
- `prepare_dispatch`: verify exact current record/revision/digest and stored authorization, current authority, and live Expert grant dependency under the transaction. Invoke `prepare_action_dispatch`. Persist immutable ExecutionIntent and Executing together before returning. First successful insertion returns `DispatchAdmission { intent, record_revision, dispatch_required: true }`. A matching existing immutable execution returns `dispatch_required: false`; changed immutable identity conflicts. Do not compare new wall-clock `now` against a historical identical replay in a way that could generate a new execution. No caller receives true twice.
- `load_execution`: exact Person/execution lookup returns its immutable stored intent and current record revision, always `dispatch_required: false`. Do not reconstruct intent from current source/policy or expiry. Invalid/absent stored intent fails closed.
- `settle_execution`: exact settlement retry is keyed by execution ID plus `expected_revision`, with a digest of the complete outcome and Person/effect identity. Same historical settlement returns current associated ActionRecord before current revision checks; different outcome under that same expected revision conflicts. A new current-revision settlement invokes `settle_action`, storing outcome and resulting record atomically. Success includes the CollectionTicket in the same commit. New evidence may settle Unknown at its new current revision. Executing/Unknown are never erased by lock, grant/policy revocation, timeout or cancellation. Terminal success cannot later become failure/unknown.
- `pending_recovery`: bounded pure enumeration of `ActionRecord::pending_recovery()` (Executing, Unknown, success with pending collection); no mutation or auto-dispatch.
- `ack_collection`: only exact Person/execution/receipt digest and ticket revision plus a bounded durable Day projection ref. Invoke `acknowledge_action_collection`; persist record/ticket together. Exact prior acknowledgement joins even though ticket revision advanced. A changed projection ref/digest under the same ticket receipt conflicts. It never changes execution/approval authority.
- `read_authority`: one encrypted snapshot only, default revision 1 only on proven absent valid schema.
- `compare_and_set_authority`: command receipt first; exact changed mode/expected revision/person digest. Invoke `change_action_authority` on a new command and atomically persist authority, receipt, and all required pending/approved record invalidations using `invalidate_action_policy`. When requested mode already equals current mode, the helper returns the unchanged revision: persist the new command receipt, but do not invalidate records for that no-op. Executing/Unknown and settled effects are preserved. Replay never increments authority twice.

Keep a single command namespace for submit/decision/reconcile/authority. Settlement and collection receipt keys may be separate physically but must preserve their full exact replay binding. Do not silently replace an uncertain command receipt or manufacture a new Action/ExecutionId.

## Native revision/evidence distinction

CalendarExternalRevision is tagged: ProviderOpaque or ObservationFingerprint. EventKit's existing native prewrite revision is a SHA256 observation fingerprint recomputed immediately before save/remove, so Actions deliberately accepts that variant for its admitted EventKit executor. Never relabel it ProviderOpaque or assert provider atomic CAS. Hosted fingerprints do not grant writes. Normal EventKit Create/Update/Delete remain available, while ambiguous acknowledgements remain Unknown. Storage never queries EventKit or tries to infer outcome from event absence/current content.
