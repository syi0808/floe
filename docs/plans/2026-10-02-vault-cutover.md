## 1. What the baseline actually does

1. `TursoStore` (`src/engine.rs:10`) is a separate, unencrypted local database. It stores Day captures/events/tasks/notes/mirrors, source connections, Calendar action projections and an Action authority projection. `FloeCore::open` constructs it independently of Vault unlock (`crates/app/src/core.rs:23`); SourceConnectionService and DayService use it. Do not silently make all source metadata/Day availability depend on unlocking encrypted agent state.
2. `EncryptedAgentVault` (`src/vault.rs:95`) stores Sessions, Runs, journal, interactions, grants/cleanup, Tasks/registry, Knowledge, agent Action envelopes, owner keys, producer pin and consumed challenges. Source rows are not in this database. There is no atomic transaction spanning those two databases, OS Keychain and Go.
3. Despite its crate comment, Vault contains substantial business orchestration: Conversation admission/state/projection, Experts install/configure/binding, Knowledge discovery/review/job policy, native Calendar grant policy, remote wire parsing and Access policy. Move these to their owners; do not merely rename the adapter facade.
4. `vault/expert_actions.rs:97 with_proposal_evidence` commits at lines 244–246 before invoking `operation(evidence).await` at 248. The proposed callback removal improves the explicit boundary and exact replay, but a claim that this baseline holds its transaction over that callback is false. `TransactionLearningEvidence` also awaits only local SQL while its transaction exists. Preserve that fact rather than manufacturing a defect.
5. Current transaction finishing is inconsistent: Access and checked registry finishers latch uncertain storage/key failure, while Learning and archive finishers can ignore rollback failures. Consolidate physical transaction settlement under one private fail-closed helper, preserving Conflict as a retryable exact-CAS conflict and an uncertain commit as unknown until readback. Never replace a key or database to recover.

## 3. Exact cross-database source-review and disconnect contract

### 3.1 Owners and records

Connections owns `ConnectionReviewApply` and `ConnectionDisconnect` operation lifecycle at `crates/modules/connections/src/domain/source_operation.rs`; orchestration is `application/source_operation.rs`. Access owns `ConnectionReview`, `GrantCommit` and its durable result at `crates/modules/access/src/domain/connection_review.rs` and `ports/grant_repository.rs`. They are distinct concepts: an operation reservation prevents conflicting configuration; it never grants Observe.

`ConnectionReview` is encrypted and stores `ReviewRef { id, revision, digest }`, admitted Person/device, exact stable source, expected local source revision/SourceAuthority, exact physical resources and native/provider subject, Gateway producer binding where applicable, expiry, each logical View's expected grant including absence, consumer/purpose/categories, requested `DeviceOnly | GatewayAllowed { categories }`, and policy digest. Only Access constructs/revalidates it. The product echoes its opaque reference and decision. Secrets and model profiles are absent.

`SourceOperationRecord` has `kind: ConnectionReviewApply | ConnectionDisconnect` and stores operation ID, command ID, exact source identity, expected source revision/authority, compare-only review reference/digest, typed kind and phase, operation revision and non-secret receipt identity. It does not copy permission scope, provider payload or bearer into the source database. `SourceOperationPhase = Reserved | GrantCommitted { receipt_id, receipt_digest } | CleaningUp { receipt_id, cleanup_revision } | Completed { receipt_id } | Aborted { reason } | RepairRequired { receipt_id, reason }`. `Reserved`, `GrantCommitted`, `CleaningUp`, and `RepairRequired` retain the exclusive source-use/mutation fence; only `Completed` and a proven pre-grant `Aborted` release it. RepairRequired is a visible stop, never an expired lease. One fence-holding reservation per source is enforced physically. Source metadata remains readable; new source use and source edits fail closed while its operation is unresolved. A failed or crashed process cannot leave a grant usable under a half-applied source operation.

At `crates/modules/connections/src/ports/source_operation_repository.rs`:

```rust
trait SourceOperationRepository: Send + Sync {
    async fn reserve(&self, request: SourceOperationReservation)
        -> Result<SourceOperationAdmission, SourceRepositoryError>;
    async fn load_operation(&self, id: Uuid)
        -> Result<Option<SourceOperationRecord>, SourceRepositoryError>;
    async fn compare_and_swap_operation(&self, change: SourceOperationChange)
        -> Result<SourceOperationRecord, SourceRepositoryError>;
    async fn pending_operations(&self, limit: usize)
        -> Result<Vec<SourceOperationRecord>, SourceRepositoryError>;
}
```

`reserve` atomically checks current source identity/revision/authority, expected absence for reviewed native creation where applicable, operation/command exact replay and absence of another nonterminal reservation. `SourceOperationChange` contains exact expected operation revision, source expectation and owner-validated next phase; completion may include the single owner-produced source successor. The source update and reservation phase commit together in the source database. Every SourceRepository mutation uses this same reservation discipline. No optional bypass constructor remains.

At `crates/modules/access/src/ports/grant_repository.rs`:

```rust
trait GrantRepository: Send + Sync {
    async fn read_review(&self, reference: ReviewRef)
        -> Result<ConnectionReview, AgentFailure>;
    async fn store_review(&self, review: ConnectionReview)
        -> Result<ReviewRef, AgentFailure>;
    async fn snapshot(&self, source: GrantSourceBinding)
        -> Result<GrantSnapshot, AgentFailure>;
    async fn commit(&self, command: GrantCommit)
        -> Result<GrantCommitReceipt, AgentFailure>;
    async fn receipt(&self, query: GrantReceiptQuery)
        -> Result<Option<GrantOperationReceipt>, AgentFailure>;
    async fn abort(&self, command: GrantAbort)
        -> Result<GrantAbortOutcome, AgentFailure>;
}
```

`GrantCommit` has operation/command identity, request digest, exact review reference (for expansion), source reservation identity, every expected grant ID/authority or expected absence, and owner-produced mutations. The adapter reloads review and exact grants, invokes Access's pure `validate_commit`, checks the current key, atomically applies the entire bundle, records cleanup/invalidation and stores `GrantCommitReceipt`. The receipt binds source operation/review/request digest and all resulting grant authorities. Same operation+same digest returns the existing receipt; changed content conflicts. Expected absence is checked against every non-revoked exact logical resource, rejecting duplicate live authority. Grant IDs are not freshly substituted during replay.

### 3.2 Sequence and crash matrix

1. Connections/Access obtain current native/provider evidence outside SQL transactions and revalidate exact reviewed fields. Drift supersedes the review; do not refresh the expected source or grant underneath approval.
2. Connections reserves the source operation with exact local source expectation. This is a lifecycle barrier, not a held database transaction. Current source-use admission reads and rejects a nonterminal reservation; late/in-flight results still pass existing live source/grant release fences.
3. Access commits the reviewed grant bundle and durable receipt in its encrypted transaction. For disconnect, the command revokes **every non-revoked grant, including Paused**, and invalidates only not-yet-dispatched Actions. Executing/Unknown Actions remain durable and reconcile lookup-only.
4. Connections reads/rejoins that exact receipt, re-observes external continuity if necessary, and completes the operation/source successor by CAS. Observe enable never edits source resources or SourceAuthority. Source-only configure never changes grants. Provider/native subject change advances SourceAuthority exactly once through Connections' successor validator.
5. Disconnect performs external cleanup only after durable revocation receipt; record each result under the same operation. A lost cleanup acknowledgement does not report remote revocation or delete uncertain Actions. Pending operation continues to block source use until exact cleanup/terminal reconciliation. Local Gateway forget remains explicitly distinguishable from remote credential revocation.

Crash before Access commit: reservation is pending and source use blocked; load `receipt(GrantReceiptQuery)`, then repeat only the exact authorized commit if still valid. Crash after grant commit/before source-operation completion: receipt readback settles the existing commit, never increments grant authority again. Changed/expired source with no observed receipt: request the exact Access abort CAS below; absence is not proof that a commit cannot land. Only a durable Aborted receipt permits source supersession without grant expansion. Changed source after a receipt: keep blocked and report repair/conflict; do not silently restore permission or pretend atomic rollback across databases. A deliberately superseded/disconnected source must remain unusable until a fresh owner review or exact revocation reconciliation settles it. Vault locked: metadata reads continue, but grant mutation/review and dependent source use stay unavailable; no fallback store.

`GrantCommitReceipt` contains operation ID, command ID, immutable request digest, reservation ID/generation, source identity/revision/authority, ReviewRef (or disconnect kind), commit ID, resulting grant IDs/authorities/states and cleanup IDs. `receipt(GrantReceiptQuery)` compares every supplied replay expectation, not merely operation ID. Access receives an Access-owned immutable `SourceReservationEvidence` issued by the Connections service via an inward Access port; Access does not import Connections or query its SQL. The durable race protocol is `GrantOperationSlot { operation_id, request_digest, reservation_id/generation, state: Committed(GrantCommitReceipt) | Aborted(GrantAbortReceipt) }`, physically unique by operation ID in the encrypted Access transaction. `commit` and `abort` each insert/compare this same slot in their atomic transaction; there is no externally visible provisional slot needed. Commit atomically installs grants plus Committed slot only if no Aborted slot exists. Abort atomically inserts the no-grant Aborted tombstone if no Committed slot exists; if a committed receipt already exists it returns `GrantAbortOutcome::AlreadyCommitted(GrantCommitReceipt)` for reconciliation. Exact repeated abort rejoins its same receipt. Changed operation digest/reservation always conflicts. `GrantAbortReceipt` binds operation/command/request digest/reservation/source expectations and proves no grant mutations committed for this operation; it never deletes historical grants. Therefore commit and abort are mutually exclusive even across host crashes. `GrantReceiptQuery` contains operation ID, expected request digest, reservation ID/generation and exact source expectation. `GrantAbortOutcome = Aborted(GrantAbortReceipt) | AlreadyCommitted(GrantCommitReceipt)`; both compare the same replay fields. `GrantOperationReceipt = Committed(GrantCommitReceipt) | Aborted(GrantAbortReceipt)` makes negative lookup distinct from proven no-grant abort. Connections may mark its source phase Aborted and release the fence only after matching Aborted receipt, never after `receipt=None`, timeout, lock, process cancellation or an in-memory guard. A source reservation thus cannot disappear while an Access commit may still land. Source mutation/disconnect racing an active apply must first settle or fence that operation; it cannot silently replace its reservation. After receipt commit, cancel cannot turn the operation into Aborted. If the source completion CAS is unknown, read both records before repeating only that CAS. A lost Access commit response always requires receipt readback before considering another commit; an unavailable or locked Vault leaves the source fenced.

**S1 recovery clarification (2026-10-02):** Receipt lookup and durable abort use Access-owned `GrantOperationIdentity { operation_id, command_id, device_id, request_digest, reservation_id, reservation_generation, source: GrantSourceBinding, source_revision: Option<u64>, source_authority: SourceAuthority }`. `GrantReceiptQuery { identity }`, `GrantAbort { identity }` and `GrantAbortReceipt { identity, abort_id }` compare every supplied identity field in the same unique encrypted operation slot. The original admitted caller device is retained as nonsecret operation metadata and compared on every replay, receipt, abort and permission reduction; remote producer identity never substitutes for it. Complete reservation evidence also verifies that the native execution owner or verified Gateway binding belongs to that same device. Connections reconstructs this identity from its durable reservation without copying physical resources, native/provider subjects or permission payloads into Turso. `GrantCommit` retains the complete `SourceReservationEvidence` and exact stored review/current source evidence; a committed receipt derives its lookup identity from that evidence. An abort proves no grant mutations for the exact operation and requires no fresh external observation. Commit and abort remain mutually exclusive under the same slot, including a crash before the first receipt. Observe Pause is an explicit permission reduction (`ConnectionObservePause` / `GrantCommitKind::PauseObserve`) through the same source fence and receipt protocol: only Active grants become Paused with authority advancement and invalidation, while Paused/Revoked grants remain unchanged. It never means Disconnect or grants processing expansion.

The reservation is recovered before accepting new source use on host start. It is neither a lease that expires into permission nor a second grant. For remote source changes outside Rust's control, exact signed provider/source preflight and post-I/O fences still apply; local reservation cannot prevent remote drift and never claims to do so.

## 6. Gateway signing split without weakening authority

`vault/remote_authority.rs` currently owns strict JSON/base64/wire parsing, producer signature checks, owner key crypto, pairing lifecycle, grant-purpose policy and SQL replay storage. Split it as follows:

Producer audience remains transport identity; it is not the deleted downstream model-recipient consent.

No raw private key return across an owner or Gateway adapter seam. `commit_pin` takes the exact reviewed producer/key, operation ID/digest and expected pin revision; `readback(operation_id)` returns its immutable receipt for exact comparison, never a mutable trust map.

At Access `ports/authorization_signer.rs`, use `AuthorizationSigner::{public_key, sign_authorization}`; Connections `ports/gateway_pairing.rs` uses `EnrollmentSigner::{public_key, sign_enrollment, readback}`. The Vault adapter revalidates key/pin, consumed operation identity, clock and local grant expectations in a short transaction, commits the signing receipt, checks key health, signs exact bytes privately and returns only public key ID/signature. Replaying the same enrollment operation reads the identical receipt/signature or deterministically reproduces the same signature after exact receipt comparison; altered bytes/producer/identity conflict. Do not reissue a different challenge to hide a lost acknowledgement.

Runtime admission/release challenge replay stays single-use; bounded receipt readback is not permission to dispatch twice. Preserve signed domain separation `floe.remote.producer.v1\0` and `floe.remote.authorization.v1\0`, issuer enrollment separation, logical resource vs exact physical resources, source/grant epoch comparison, result/query digest and admission-release linkage. No raw credentials are added to these owner records. A postcommit key failure returns no signature and leaves the durable receipt for exact recovery; never regenerate the owner key.
