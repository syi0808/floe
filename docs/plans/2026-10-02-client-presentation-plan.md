## Ownership map and planned treatment

- `design_tokens`, theme, widget-state mapping, motion, fields, primitive wrappers, squircle, badge, button and custom controls remain one shared presentation system. They delegate intent through callbacks and must not acquire Rust authority, source-grant policy or external-write decisions.
- `FloeApp` is composition: it passes owner gateways/native APIs and a query into `PersonalDayScreen`, wraps a toast host and configures English localization/theme. Runtime teardown is callback-based and unawaited.
- `FloeToastHost` owns presentation lifetime, stack layout and optional action callbacks only. Expiry/dismissal must not become backend operation cancellation or success authority.
- Preview fixtures use in-memory `FakeDayGateway` and `DayAppearance`; the catalog uses production components. Preserve these manual review paths when planning test deletion.
- `DesignFeedbackOverlay` is real debug tooling with keyboard and native-channel lifecycle, rendered text/selector collection, temporary PNG capture, clipboard export and diagnostics integration. Debug/release composition policy belongs to its caller, not an assumption based on the preview directory.
- `app_en.arb` is resource authority; `app_localizations.dart` and `app_localizations_en.dart` are generated coupled production code. Later changes must update owner copy/callers and regenerate consistently, never hand-edit the generated pair.
