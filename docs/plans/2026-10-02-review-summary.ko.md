# Floe 구조 개편 계획 검토 요약

상세 실행 규격은 [주 계획](2026-10-02-architecture-refactor.md), 정확한 메서드·DTO·의존성은 [공통 계약](2026-10-02-canonical-contracts.md), 변경 전 심벌과 호출자는 각 영역의 cutover 문서 및 JSON 지도에 있습니다. 세 결정은 13:46 UTC에 확정됐고, 전체 계획의 순차 실행도 13:49 UTC에 승인됐습니다. 이 문서 수정 작업 자체에서는 구현·삭제를 실행하지 않습니다. 최종 정적 검토 상태는 [검토 기록](2026-10-02-plan-review.md)을 따릅니다.

## 먼저 고정할 구조

- Flutter는 사용자의 의도와 안전한 화면 상태만 다룹니다. AppWire/FFI는 입력 형태와 입출력을 변환하고, Rust의 해당 도메인 서비스가 판단합니다.
- Conversation·Memory/Knowledge·Experts·권한·Actions 승인은 Rust가 소유합니다. `floe-app`은 실제 구현의 생성, 수명 관리, 검증된 호출 전달만 담당합니다.
- Gateway 어댑터가 Rust의 비공개 자격 증명을 사용합니다. Go는 원격 추론, 소스 취득, provider 비밀을 담당합니다. provider API 키와 OAuth refresh token은 Go에 남습니다.
- Pairing에 authority enrollment를 합칩니다. Rust가 시작·확인·관찰·취소·저장 복구를 소유하며 별도 RemoteAccess 흐름과 Flutter의 HTTP/credential bridge를 없앱니다. Pairing 성공은 소스 읽기 허용이 아닙니다.
- Go의 trust, runtime authority, integrations, views, inference를 구분합니다. connector는 도메인 포트에 맞춰 구현하고 node에는 조립만 남깁니다. 현재 범위에 Go Actions나 원격 쓰기 도메인을 추가하지 않습니다.

## 의존성에 맞는 실행 순서

1. **P0: 계획 검토.** 고정된 main 커밋 `3f4b407f8079d611224cd7adbef121f9e7e75e8e`의 추적 파일 1,172개를 확인했습니다. 현재 작업은 문서 작성과 정적 분석뿐입니다.
2. **T0: 승인 후 기존 테스트 기록·제거.** 각 assertion/table case를 출처, 전제, 입력·행동, 기대 결과, 실패·경계조건으로 먼저 기록합니다. 기존 주장과 새 요구사항을 구분하고, 그 뒤에만 Git으로 복구 가능한 테스트 코드와 전용 지원 파일을 제거합니다. 지금 테스트를 지우거나 새로운 테스트를 작성하지 않습니다.
3. **S1: 첫 Conversation 수직 구조를 한 번에 닫습니다.** 계약·의존성 → 신원/Pairing/비공개 자격 증명 → 소스 처리 권한/Health 전처리 → Rust·Go inference wire와 공통 선택기 → Conversation의 Run/interaction 소유권 → Flutter/FFI/CLI/native 호출자 → 구 경로 삭제 순서입니다. 이 묶음 안에서 잠시 안 맞는 호출자는 마지막 단계까지 함께 바꿉니다.
4. **G1: 완성된 S1 경계에서만 포맷·컴파일합니다.** 작은 변경마다 반복 검사하지 않습니다. 테스트와 전체 앱 패키징/빌드는 하지 않습니다.
5. **S2: 나머지 구조를 닫습니다.** Go 소스 소유자 → Connections/Access/Context/Day → Experts 공통 Runtime → Knowledge/Actions → App/node 조립 정리 → 모든 caller/export/manifest/문서 잔여 경로 제거 순서입니다.
6. **G2: 전체 구조가 완성된 뒤 포맷·컴파일·전체 빌드 성공을 확인합니다.** Apple 플랫폼 검증은 필요한 SDK/서명 환경이 갖춰진 곳에서 수행하고, 실행하지 못한 부분은 따로 남깁니다.
7. **S3/G3: 그 다음 새 테스트를 설계하고 검증합니다.** 새 소유권, 오류·취소·재시도·불확실성·복구 계약에 맞춰 작성하며, 구 테스트 통과 자체를 완료 조건으로 삼지 않습니다.

## 설계에서 구체적으로 해결한 부분

- Gateway Primary가 유효한 계획 관찰에서 실제로 없는 경우에만 local Fallback을 선택합니다. timeout, 자격 증명 거절, 정책 거절, 잘못된 inventory는 Fallback 이유가 아닙니다.
- 소스 처리 권한은 DeviceOnly/GatewayAllowed로 판단합니다. Health는 추론 전에 source-local 변환을 거치며 HighlySensitive 분류를 유지합니다.
- 소스 검토 때문에 멈춘 Run은 `Blocked`로 저장합니다. 모델 답변이나 사용량을 만들어내지 않고 실제 실행 내역을 보존합니다. 검토 해결 뒤 원래 사용자 메시지를 중복 추가하지 않는 새 자식 Run을 정확히 한 번 연결합니다.
- Connections 메타데이터와 암호화된 Access 저장소를 하나의 가짜 원자적 트랜잭션으로 취급하지 않습니다. 소스 fence와 상호 배타적인 commit/abort 영수증을 이용해 복구하며, 영수증이 없거나 timeout이라는 이유로 fence를 풀지 않습니다.
- Experts는 내장 패키지까지 같은 Package → Installation → Directory → Task → Runtime 경로를 씁니다. 별도 model/reasoner 루프와 패키지 이름으로 권한을 고르는 분기를 없앱니다.
- Actions는 승인된 정확한 효과를 실행 전 영속화하고, 확실히 미적용된 실패와 결과를 모르는 상태를 나눕니다. 응답 유실 후 무조건 다시 실행하지 않으며, 결과 수집은 외부 효과 재실행과 별도입니다.

## 확정된 결정 (2026-10-02 13:46 UTC)

1. **단일 암호화 Actions 저장소를 채택합니다.** Direct와 Expert를 하나의 ActionsRepository로 합치며, Vault가 잠겨 있으면 외부 Action의 검토·실행·복구를 사용할 수 없습니다. 일반 Day 로컬 CRUD는 별도입니다.
2. **현재 loopback Gateway 배포 범위를 유지합니다.** 이번 구조 개편에 임의 원격 URL/TLS/새 배포 체계를 추가하지 않습니다.
3. **기존 Floe 개발 데이터는 버려도 됩니다.** 깨끗한 새 프로필·스키마를 목표로 하며, 하위호환만을 위한 데이터 보존·이전·구 런타임 유지 요구는 없습니다.

이번 변경은 계획 문서에 결정을 반영하는 작업입니다. 지금 데이터·키·프로필·제품·테스트 파일을 삭제하거나 초기화하지 않습니다. 나중에 영구 삭제를 실행할 때는 정확한 로컬 Floe 대상과 실행 시점의 확인이 필요하며, 외부 provider·캘린더·메일 데이터는 범위에 포함되지 않습니다. 실제 초기화 전에는 진행 중이거나 결과가 불확실한 외부 작업이 새 프로필에서 중복 실행되지 않도록 좁은 위험 점검을 합니다. 이를 이유로 구 데이터나 구 런타임 전체를 보존·이전하도록 요구하지 않습니다.

새 시스템에서 발생한 외부 효과의 실행 전 기록, 불확실성 구분, 정확한 복구 원칙은 계속 유지합니다. 13:49 UTC에 전체 계획의 순차 실행이 승인됐습니다. 테스트별 동작 기록을 완성한 뒤 제거한다는 선행조건은 그대로이며, 현재 문서 수정 단계에서는 구현·삭제를 실행하지 않습니다. 영구 데이터 삭제와 자격 증명 변경은 해당 작업의 정확한 대상·시점에 맞는 별도 확인이 필요합니다.

## 증거의 범위

텍스트 1,132개를 전체 읽고 이미지·폰트 등 바이너리 40개를 형식에 맞게 확인했습니다. 폰트는 구조/메타데이터를 확인했으며 모든 글리프를 렌더링한 것은 아닙니다. Git 내부 메타데이터는 제품 추적 파일 집계에 포함하지 않았습니다. 추적 제품·테스트 파일 변경은 없고, 포맷·컴파일·빌드·테스트를 실행하지 않았으므로 런타임 성공을 주장하지 않습니다.

CP07/08은 대화에서 진행 중이라고 보고된 작업입니다. 확인한 main 스냅샷에는 해당 cutover가 반영되지 않았습니다. 별도 로컬·미푸시 작업의 존재나 실패를 추정하지 않으며, 이후 제공되는 변경은 구현 전에 이 기준과 합쳐야 합니다.
