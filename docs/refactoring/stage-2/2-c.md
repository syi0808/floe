# 2-C — Delegation Ownership Convergence

**Status: complete · frozen**

**Code baseline reviewed:** 7a6b2fb2e1063a6f55ce8d2569f5a73bd6e47681  
**Plan revalidated on main:** f9bc3cda28391fe99455904233df4ce3509a9c6e

This document is the authoritative execution plan for 2-C.

2-B is complete/frozen. Do not reopen model/projection/tool architecture unless a new P0 is directly exposed by delegation convergence.

## Goal

Remove the final General Conversation internal bridge:

~~~text
Engine
  → LegacyDelegationPort
  → App stage(run_id, context)
  → Experts TaskCoordinator
  → App endpoint removes staged context
~~~

and converge on:

~~~text
Engine
  → TaskCoordinator : DelegationPort
  → Experts-owned durable Task
  → Directory-resolved AgentEndpoint
  → explicit bounded EndpointInvocation
  → ExpertReport
  → Task terminal receipt
~~~

App may construct endpoints and concrete source/model dependencies. It must not maintain mutable run-id → endpoint-context authority or intercept each delegation to make the Task executable.

At 2-C exit:

- LegacyDelegationPort production references = 0;
- ScheduleEndpoint and BuiltinExpertEndpoint have no stage()/clear() context maps;
- the exact endpoint execution context is explicit, bounded, secret-free and bound to the durable delegation;
- TaskCoordinator remains the single Task admission/lifecycle/replay/cancellation owner;
- stable TaskId / InvocationKey semantics from 2-B remain unchanged.

## Current debt

### Legacy bridge

The root turn currently constructs LegacyDelegationPort with:

- TaskCoordinator;
- ScheduleEndpoint;
- BuiltinExpertEndpoint;
- the whole ConversationTurnRequest;
- AgentContext;
- session id;
- output bound.

The bridge chooses Schedule vs builtin by agent id, writes a context into an App HashMap keyed by parent run id, calls TaskCoordinator, then clears the map.

This creates authority outside the Task contract and creates a crash-sensitive dependency on ephemeral App state.

### Builtin staged context

BuiltinExpertEndpoint currently stores:

~~~text
BuiltinExpertEndpointContext {
  ConversationTurnRequest,
  AgentContext,
  session_id,
  max_output_bytes,
}
~~~

in Mutex<HashMap<run_id, ...>>.

The endpoint consumes this hidden state to obtain:

- device id;
- session id;
- AgentContext;
- max output bytes;
- saved server connection source.

### Schedule staged context

ScheduleEndpoint similarly stores:

~~~text
ScheduleEndpointContext {
  ConversationTurnRequest,
  AgentContext,
  max_output_bytes,
}
~~~

and additionally uses the root ConversationTurnRequest.text as schedule planning input.

ADR 0018 says an Expert receives the Manager delegation message as its assignment, not the full Manager conversation. Schedule must therefore plan from the admitted DelegationRequest.message, not from the original root prompt.

## Revalidated residual inventory

The current main call graph was rechecked before execution. The remaining work is concrete and bounded:

- `TaskCoordinator<Repository>` already implements `DelegationPort`; 2-C must wire the root directly to that existing implementation, not add another coordinator/adapter.
- `TaskCoordinator::execute` currently computes `TaskRecord.request_digest` from the full serialized `DelegationRequest`, while Engine replay verification and Conversation recovery still use `input_digest(&request.message)`. C1-C3 must converge these onto one canonical request digest without changing TaskId/InvocationKey derivation.
- `ValidatedModelBatch` currently persists projection coverage and pinned revisions but has no delegation execution-context binding. The binding added by C1/C2 must therefore become part of batch validation/equality and resume/cross-run reconciliation.
- `BuiltinExpertEndpoint` still owns `Mutex<HashMap<Uuid, BuiltinExpertEndpointContext>>` and removes the staged value during `AgentEndpoint::execute`.
- `ScheduleEndpoint` still owns the equivalent run-id context map and still calls `schedule::plan_run(&staged.request.text, ...)`; this is the root-prompt dependency C5 must delete.
- root `run_general_turn` still constructs `LegacyDelegationPort` and hands it the whole `ConversationTurnRequest`, `AgentContext`, session id, and output bound.
- `AgentContext` is already defined/exported by `floe-agent-contract`; using it in `DelegationExecutionContext` does not require a new Context→contract dependency or a duplicate context type.
- `OpenVault::sync_expert_directory` still registers builtin agent ids with `self.builtin_expert_endpoint.clone()`; therefore the builtin endpoint Arc may remain as Directory-owned composition state after root `ConversationTurnInputs` stops carrying it. Do not delete that field merely to satisfy a grep gate.

These facts are the implementation baseline. If code differs when the agent starts, update this inventory in-place only when the difference materially changes a 2-C exit gate; do not create another planning document.

## Fixed design decisions

### 1. Explicit execution context belongs to the delegation contract

Add a bounded secret-free contract in floe-agent-contract, suggested name:

~~~rust
pub struct DelegationExecutionContext {
    pub session_id: Uuid,
    pub device_id: String,
    pub agent_context: AgentContext,
    pub max_output_bytes: usize,
}
~~~

Equivalent naming is acceptable.

Required validation:

- session_id non-nil;
- device_id trimmed, non-empty, bounded to the existing device-id limit;
- agent_context.validate() succeeds;
- max_output_bytes in 1..=MAX_OUTPUT_BYTES;
- serialized context has an explicit upper bound suitable for journal persistence.

The context must not contain:

- SavedServerConnection;
- token/bearer;
- base URL/endpoint;
- model profile/placement;
- recipient/consent;
- provider route;
- cancellation/deadline — ExecutionScope already owns these.

### 2. DelegationRequest carries the explicit context

Extend DelegationRequest with the execution context.

The request already carries stable Task identity, parent Run, principal, agent/revision, assignment and context refs. Adding the execution context makes everything needed for endpoint invocation explicit and journal-visible.

Do not put App ConversationTurnRequest into agent contracts.

### 3. Bind execution context to ValidatedModelBatch for crash/cross-run safety

EngineRequest receives an optional delegation execution context from the Conversation owner.

When a validated model batch contains a Delegate step:

- a valid delegation context is required;
- ValidatedModelBatch stores the exact delegation context, or an equivalent exact durable binding;
- resumed execution uses the context stored with the validated batch, not a freshly assembled replacement;
- full batch equality used by cross-run takeover includes this binding.

When a batch has no Delegate step, do not persist unnecessary delegation context.

This prevents:

~~~text
validated batch
→ crash
→ changed device/context
→ same TaskId executing with different host context
~~~

### 4. DelegationIntent must exactly match the batch-bound context

When Engine constructs DelegationRequest for a Delegate step, use the context bound to that ValidatedModelBatch.

Conversation recovery must validate:

- model-produced agent id/revision/message/context_refs still match the current validated step;
- stable invocation_key/task_id still match execution+batch+ordinal;
- DelegationRequest execution context equals the batch-bound context;
- malformed context fails closed as StorageUnavailable during journal projection.

Do not silently reconstruct missing context.

### 5. One canonical delegation request digest

Today TaskCoordinator hashes the serialized DelegationRequest while Engine replay receipts use only message text as input_digest.

2-C must define one canonical delegation request digest, suggested API in floe-agent-contract:

~~~rust
pub fn delegation_request_digest(request: &DelegationRequest) -> [u8; 32]
~~~

It must cover at least:

- principal / parent linkage;
- selected agent + definition revision;
- assignment message;
- context_refs;
- explicit execution context.

Stable TaskId and InvocationKey remain separate identity fields and must also be checked exactly.

Use this digest consistently for:

- TaskRecord.request_digest;
- TaskCoordinator replay validation;
- Engine ReplayReceipt.input_digest for delegation;
- Conversation recovery replay generation/validation;
- cross-run resumed Task replay.

A changed device/session/context must conflict rather than reuse a prior Task result.

### 6. Conversation passes context without owning Expert policy

App already has the runtime values. Build DelegationExecutionContext in root composition and pass it through Conversation TurnRequest/EngineRequest without interpreting Expert meaning.

Recommended flow:

~~~text
App run_general_turn
  → DelegationExecutionContext {
      session_id,
      device_id,
      agent_context,
      max_output_bytes
    }
  → Conversation TurnRequest runtime field
  → EngineRequest
  → ValidatedModelBatch
  → DelegationRequest
~~~

This runtime context must not become part of CanonicalTurnIntent/request identity. Duplicate command identity stays user intent, exactly as device/credential state is excluded today.

Conversation may validate and forward the context; Experts owns how an endpoint uses it.

### 7. TaskCoordinator stays the single lifecycle owner

Do not create a replacement delegation coordinator.

TaskCoordinator continues to own:

- Directory eligibility/revision resolution;
- Task admission;
- Submitted → Working → terminal transitions;
- executor generation;
- active Task cancellation;
- exact replay;
- endpoint result validation;
- atomic settlement through TaskRepository.

The production root DelegationPort after 2-C is TaskCoordinator itself.

### 8. EndpointInvocation is self-sufficient

AgentEndpoint::execute must require no App side lookup keyed by run id.

Builtin endpoint reads from invocation.request.execution_context:

- session id;
- device id;
- AgentContext;
- max output bound.

Schedule endpoint reads:

- device id;
- AgentContext;
- max output bound;
- assignment from invocation.request.message.

Parent Run/principal/task/agent/revision remain in DelegationRequest and ExecutionScope.

### 9. Credential lookup is an endpoint dependency, never delegation data

Removing ConversationTurnRequest from staged context also removes the request-level saved-connection source.

Do not put credentials into DelegationExecutionContext.

Prepare legacy Expert model/source compatibility using an endpoint-injected saved-connection store:

~~~text
production endpoint
  → SavedServerConnectionStore / provider credential boundary

test endpoint
  → compile-time test fixture store
~~~

The endpoint then admits the loaded saved connection against:

- invocation principal;
- execution-context device id.

Test hermeticity must use constructor/dependency injection, not environment variables and not a production-exposed Fixed credential field.

This is temporary legacy Expert transport support until Stage 3-A; it is not model policy ownership for App.

### 10. Schedule assignment is the delegation message

Replace Schedule planning input based on staged.request.text with invocation.request.message.

This aligns with ADR 0018:

~~~text
Manager Delegate message
  → Expert assignment
~~~

The Expert must not depend on the root user prompt being hidden in App staging.

Add a regression where root prompt and delegation message differ and prove Schedule uses the delegation message.

### 11. Preserve direct Task coverage and settlement

ExpertReport already carries:

- result;
- artifacts;
- coverage;
- optional EndpointSettlement.

Keep that contract.

Do not move endpoint result coverage back into the Manager journal through a new side channel.

Existing internal StoreResultRecorder / TaskCoverageRecorder used while a legacy builtin Expert acquires sources may remain if still required by the endpoint implementation. Its cleanup/canonicalization belongs to later Expert/domain work unless 2-C reveals a direct Task correctness defect.

### 12. Typed terminal outcomes stay Tasks, not thrown Manager failures

TaskCoordinator keeps mapping endpoint failures to TaskState:

- CapabilityDenied / PolicyDenied / ConsentRequired → Rejected;
- Cancelled → Cancelled;
- DeadlineExceeded → TimedOut;
- Interrupted → Interrupted;
- other endpoint failure → Failed.

The Engine receives the terminal TaskReceipt. Do not convert an ordinary denied/rejected Expert into a fabricated successful Expert reply.
