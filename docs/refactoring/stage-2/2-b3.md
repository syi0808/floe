# 2-B.3 — Canonical Context Projection and Tool Vertical Slice

**Status: active**

**Code baseline reviewed:** `f4114890152c8ececfb94e8a78e7117fa4f4c4e4`

This document is the authoritative execution plan for 2-B.3.

2-B.1 and 2-B.2 are complete/frozen. Do not reopen their architecture unless a new P0 is directly exposed by this cutover. Stop after 2-B.3; 2-B.4 is a separate change set.

## Goal

Complete the second half of the General Conversation canonical runtime:

```text
Conversation durable transcript
  → Conversation typed history projection
  → Context route-neutral authorization / envelope assembly
  → AuthorizedModelProjection
  → Engine
```

and:

```text
Engine
  → ContextToolService : ToolPort
  → Context source acquisition + Access authority
  → ToolResult { coverage, artifacts, issue }
```

At the end of 2-B.3:

- `TransitionalModelProjection` has zero production callers;
- the root model projection no longer depends on App `InferencePolicyDecision`, App model placement, recipient, route or credential state;
- historical source-derived context is reauthorized before model dispatch;
- the answering model batch durably carries the projection coverage it actually used;
- root tool descriptors are defined by Context as canonical `ToolDescriptor` values;
- `LegacyToolPort` has zero production callers;
- successful tools return their coverage directly in `ToolResult`;
- the root tool path no longer records then re-queries result coverage through `ResultRecorder`;
- tool/source availability is independent from the selected model profile;
- App no longer owns `ConversationCapabilities` tool business dispatch.

## Scope boundary

### In scope

- route-neutral source/grant reauthorization needed by canonical model projection;
- typed Conversation history filtering;
- Context-owned envelope/coverage assembly;
- durable projection coverage binding to the validated model batch;
- Context-owned Manager tool catalog;
- `ContextToolService : ToolPort`;
- root General Conversation projection/tool wiring;
- deletion or disconnection of root-only transitional projection/tool bridges.

### Explicitly out of scope

Do not start:

- 2-B.4 removal of `HostInferenceRoutes.resolve()`;
- product-wide removal of `ConversationTurnRequest.remote_route`;
- legacy App `Model` removal when Expert/Stage-3 callers still use it;
- `LegacyDelegationPort` removal;
- staged Expert endpoint-context removal;
- Schedule/`CalendarTurn` model convergence;
- FFI/Flutter DTO cutover;
- broad 2-B integrated audit (belongs to 2-B.5).

A pre-resolved remote source route may remain temporarily for source/Expert adapters. It must no longer determine the Manager tool catalog or root model projection policy.

## Current production debt

### Projection

The root path currently wires:

```text
Engine
  → TransitionalModelProjection
      → App InferencePolicyDecision
      → App AgentContext
      → GovernedSessionStore committed coverage lookup
  → InferenceService
```

`TransitionalModelProjection` was written while `LegacyModelPort → GovernedModel` still performed history authorization later. The root no longer uses that model bridge after 2-B.2.

Therefore 2-B.3 must make the canonical projector itself authoritative for history/source reauthorization instead of relying on a removed downstream step.

### Tool

The current root tool path is:

```text
Engine
  → LegacyToolPort
  → ConversationCapabilities
      → capability-id match in App
      → personal/remote source reads
      → ResultRecorder side effect
  → GovernedSessionStore.result_coverage(call_id)
  → ToolResult
```

The coverage is correct only through a mutable side channel. The target is for the source read itself to produce the dependency that becomes `ToolResult.coverage`.

## Fixed design decisions

### 1. Context reauthorization must be route-neutral

Model profile/recipient selection happens later in Inference. Context projection must not know a model placement.

Today `DependencyAuthorization` carries:

```text
allowed_placements
deadline
cancellation
```

and personal/remote reauthorization uses model placement as part of source validity. This forces Context to know route policy.

Refactor the dependency authorization contract to mean **current source/grant/dependency authority only**:

```text
deadline
cancellation
```

Remove model placement from this contract.

Required ownership after the split:

- Context / dependency resolver:
  - source identity;
  - grant authority;
  - producer/source authority;
  - observation/freshness;
  - consumer policy;
  - lease/query lineage.
- Access model dispatch:
  - Device vs exact External target;
  - `ProcessingRestriction`;
  - exact external recipient/categories;
  - data-class release restrictions.

Do not create a second permanent `DependencyAuthorizationV2`. Change the canonical contract and migrate the finite callers.

### 2. Move target restrictions fully into Access model dispatch

After route-neutral dependency reauthorization, `ModelDispatchTarget` must enforce processing restrictions itself.

For dependent coverage:

**Device target**

- reauthorize every dependency;
- every dependency must be `ProcessingRestriction::LocalOnly`;
- `ApprovedRecipient` dependencies are denied for Device target.

**External target**

- reauthorize every dependency;
- every dependency must be `ApprovedRecipient`;
- recipient must match exactly;
- admitted categories must cover every dependency category;
- `LocalOnly` is denied.

Preserve existing external Unknown/data-class fail-close rules from 2-B.2.

This change prevents route-neutral source reauthorization from accidentally weakening model dispatch authority.

### 3. Conversation owns typed transcript filtering

Context decides whether historical coverage reauthorizes. Conversation applies that decision to its transcript.

Add a typed equivalent of legacy `project_history_into`, suggested location:

```text
crates/modules/conversation/src/application/history_projection.rs
```

Recommended shape:

```rust
struct ProjectedModelConversation {
    conversation: ModelConversation,
    authorized_history_dependencies: Vec<ContextDependency>,
}

fn project_model_conversation_history(...)
    -> Result<ProjectedModelConversation, AgentFailure>
```

Required semantics:

- current-turn entries are never removed;
- historical User entries remain even when derived history is denied;
- historical Preamble/Assistant/Tool/Delegation entries are retained only when that turn's Context decision says `retain_derived`;
- a denied/Unknown historical turn never contributes dependency coverage;
- reauthorized dependencies of retained history are returned explicitly;
- no replay receipt is preserved solely because removed history used to support it.

Do not move Session/transcript ownership into Context.

### 4. Context owns projection assembly

Add a canonical Context projection assembler, suggested location:

```text
crates/modules/context/src/application/model_projection.rs
```

It receives already-filtered Conversation input plus Context-owned/current context inputs and returns `AuthorizedModelProjection`.

It may accept a small input struct containing:

- role-scoped response contract/correction;
- canonical purpose;
- stable prompt assembly prepared by the Conversation role owner;
- filtered `ModelConversation`;
- current `AgentContext`;
- canonical root catalog;
- authorized history dependencies;
- Session input data classes;
- max output bytes.

The assembler owns:

- `ContextEnvelope`;
- contextual data;
- manifest construction;
- coverage folding;
- projection ref/revision;
- route-free validation.

It must not accept or emit:

- model profile id as authority;
- placement;
- recipient;
- endpoint/base URL;
- bearer/credential handle;
- external-transfer consent.

The existing `context_manifest` logic should move to Context or be replaced by a Context-owned equivalent for the canonical path. Legacy callers may keep their old helper until 2-D if still required.

### 5. Session data classes come from Conversation admission, not App policy

The current projection gets `input_data_classes` from App `InferencePolicyDecision`.

Canonical projection must instead use the admitted Session's data classes.

General Conversation admission already guarantees the unscoped root Session is `[DataClass::Personal]`, but do not re-hardcode that in App.

Carry the prepared Session data classes through the root composition input and hand them to the canonical projector.

### 6. Projection coverage must be durable with the validated batch

The final answer may depend on reauthorized historical source data even when no new Tool call occurred in this Run.

Current terminal coverage is derived from Engine steps only, so a canonical projector must not lose the coverage of history shown to the answering model.

Bind the answering projection coverage durably to the validated model batch.

Recommended change:

```rust
struct ValidatedModelBatch {
    ...
    projection_coverage: DependencyCoverage,
}
```

Requirements:

- `ValidatedModelBatch::validate` validates it;
- `Engine::validated_response` copies the exact `AuthorizedModelProjection.coverage`;
- journal persistence/recovery carries it unchanged;
- cross-run resume equality naturally includes it;
- an Answer executed from a resumed batch uses the same persisted projection coverage;
- no new random/projection lookup is required during recovery.

Expose the coverage of the batch that produced the final Answer through `EngineReport` or an equivalent explicit result field.

Conversation terminal coverage must include:

- final answering projection coverage;
- answer artifact coverage;
- any additional Engine-step coverage not already represented.

Duplicate exact dependencies may merge idempotently; conflicting coverage remains fail-closed.

This is a 2-B.3 provenance change, not a reopening of 2-B.1 cursor/identity design.

### 7. Unknown/stale history degrades by filtering, not by leaking or killing local chat

Projection behavior:

- Independent history → retain;
- Dependent + every dependency reauthorizes → retain and carry those dependencies;
- Unknown → keep User text only, drop derived messages;
- PolicyDenied dependency → keep User text only, drop derived messages;
- fatal storage/corruption/deadline errors → fail the projection.

The subsequent Access model-dispatch fence still validates the final retained coverage for the selected target.

### 8. Context owns the Manager tool catalog

Add one canonical Context definition source, suggested location:

```text
crates/modules/context/src/application/tools.rs
```

Expose something equivalent to:

```rust
pub fn manager_tool_descriptors() -> Vec<ToolDescriptor>
```

Current root tools to preserve:

- `people.identity.read`
- `schedule.feasibility.read`
- `attention.coarse.read`
- `wellbeing.derived.read`
- `mail.communication.read`
- `work.context.read`
- `life.logistics.read`

Context owns:

- id;
- definition revision;
- description;
- input schema;
- output data class;
- tool-id → source/query semantics.

Delete the root dependency on:

```text
CapabilityDescriptor
  → engine_ports::contract_tools()
  → ToolDescriptor
```

`AllowedCatalog.tools` must be sourced directly from Context `ToolDescriptor` definitions.

If `ScopedInstructions.available_capabilities` still requires the legacy capability shape for compatibility, derive that non-authoritative envelope summary inside Context from the same Context-owned tool definitions. Do not let it become the Manager catalog source.

### 9. Tool catalog is independent from model route

The current App exposes remote tools only when `Model::Server` and denies attention when the model is not Foundation.

Remove those conditions from the root Manager tool path.

The tool catalog is stable regardless of selected model profile.

Runtime availability comes from source/authority state:

- source configured and authorized → tool succeeds;
- source unavailable/not configured/denied → ToolPort returns the typed existing failure;
- Engine converts capability/consent/policy availability failures into a durable Tool observation as it already does.

Do not hide tools because the model ran locally or remotely.

### 10. ContextToolService returns coverage directly

Add canonical:

```text
ContextToolService : ToolPort
```

inside `floe-context`.

Recommended construction inputs:

- verified `PersonId`;
- device id;
- `PersonalGrantRecords`;
- `PersonalSourceDriver`;
- optional remote `SourceReader`;
- max output bytes if needed for early result bounding.

The service owns tool-id parsing and source/query mapping.

On successful source read:

```rust
ToolResult {
    call_id,
    text: serialized_payload,
    artifacts: vec![],
    coverage: DependencyCoverage::dependent(dependency)?,
    issue: None,
}
```

Do not:

- write coverage through `ResultRecorder`;
- ask `GovernedSessionStore.result_coverage` after the read;
- generate a second dependency identity;
- swallow a source dependency and mark the result Independent.

### 11. Personal source acquisition moves behind Context-owned tool semantics

The root Tool service must not reproduce the current App capability match.

Use existing Context personal-source functions:

- `read_people`;
- `read_feasibility`;
- `admit_attention`;
- `read_wellbeing`.

To remove App-specific People selection lookup, extend `PersonalGrantRecords` with the minimal read method it lacks today:

```text
selected_handles(grant_id)
```

and implement it in `VaultGrantRecords`.

Prefer a Context-owned helper that turns one Manager source intent into:

```text
serialized payload + ContextDependency
```

rather than seven App callbacks.

The App may inject:

```text
VaultGrantRecords
NativePersonalDriver
optional RemoteViewReader
```

but must not own the tool-id policy.

### 12. Remote source reads reuse ContextService

For:

- `mail.communication.read`
- `work.context.read`
- `life.logistics.read`

`ContextToolService` should use `ContextService / SourceReader` and preserve existing query validation.

`mail.communication.read` keeps its bounded:

- query;
- cursor;
- limit

schema.

The two other remote reads keep an empty object request.

Absence of a remote reader is `CapabilityUnavailable`, not a reason to change model routing.

### 13. Root `ResultRecorder` side channel ends here

The root tool path must not perform:

```text
record_result_independent
record_result_dependency
result_coverage(call_id)
```

to construct a ToolResult.

`StoreResultRecorder` and `ResultRecorder` may remain temporarily for Expert/Task compatibility if those callers still use them. 2-B.3 removes their **root Manager tool-path role**.

### 14. App remains composition during this slice

After the cutover, root App wiring should look conceptually like:

```text
evidence_reader = Vault ContextEvidenceReader
dependency_resolver = CompositeDependencyResolver

projection =
    ConversationModelProjection(
        evidence_reader,
        dependency_resolver,
        Context model assembler,
        current AgentContext,
        admitted Session data classes
    )

tools =
    ContextToolService(
        VaultGrantRecords,
        NativePersonalDriver,
        optional RemoteViewReader,
        person/device
    )

ConversationPorts {
    projection,
    model = InferenceService,
    tools,
    delegation = LegacyDelegationPort,
    validator
}
```

App may construct these concrete objects. It must not decide tool availability, source meaning, history retention or projection coverage.
