# 2-B.4 — App Production Cutover

**Status: complete**

**Code baseline reviewed:** 18c5bd1e2896171c96dade180225ee3e1c086b3b

This document is the authoritative execution plan for 2-B.4.

2-B.1 through 2-B.3 are complete. The canonical root model, projection, and tool paths already exist. 2-B.4 removes the remaining App-owned pre-routing and transitional General Conversation wiring so App becomes composition only.

Stop after this slice. Do not start 2-B.5 hardening in the same change set.

## Goal

The production General Conversation path must no longer pre-resolve a model route or construct App-owned model/source policy before admission.

Target:

    AppComposition::start_turn
      → Conversation intent only
      → Vault/Conversation admission
      → composition inside run_general_turn
          projection = ConversationModelProjection
          model      = InferenceService
          tools      = ContextToolService
          delegation = LegacyDelegationPort  # temporary until 2-C

No pre-turn HostInferenceRoutes.resolve(), RemoteTurnRoute, App Model::new(...), App policy(model, route), or App external_transfer_consent(...).

The canonical root model path remains Engine → InferenceService → Access model dispatch → prepared Provider transport.

The canonical root source/tool path remains Engine → ContextToolService → Context / Access → source adapter.

## What is still transitional today

### 1. Pre-turn route resolution

AppComposition::start_turn still performs HostInferenceRoutes::resolve(caller), which goes through floe_inference::select_remote_route, RemoteModelRouteResolver, /v1/inference-purposes, /v1/connectors, and produces RemoteTurnRoute before the Conversation turn is admitted.

This means a model/source observation can still block the command before the canonical runtime owns it.

### 2. ConversationTurnRequest.remote_route

The internal turn request still carries a bundle containing Inference RemoteRoute, base URL + bearer token, model placement/recipient state, pairing identity, and Connections calendar catalog.

That bundle is no longer authoritative for the root model after 2-B.2, but it still drives source/Expert setup.

### 3. Root App legacy Model/policy

run_general_turn still eagerly constructs Model::new(request.remote_route), policy(&model, request.remote_route), and ConversationExperts { model, policy, ... } even though root model/projection/tools are canonical.

The remaining eager construction is used for Expert-card filtering by model placement, legacy delegated Expert model selection, and legacy Expert source fallback policy. That is App business policy and must leave the root turn.

### 4. Dead General Conversation model bridge

LegacyModelPort, GovernedModel, transitional_budgeted_generate, legacy_conversation_messages, and contract_response no longer have a root production caller.

If repository inspection confirms no assigned non-root production caller remains, delete them in this slice rather than carrying dead General Conversation compatibility into 2-D.

## Scope

### In scope

- remove General Conversation pre-turn HostInferenceRoutes.resolve();
- remove ConversationTurnRequest.remote_route;
- separate source transport preparation from Inference RemoteRoute;
- make remote source/catalog observation lazy and source-owned;

- remove root Model::new / policy / model-consent decisions;
- keep legacy Expert execution only behind the temporary delegation bridge;

### Explicitly out of scope

- remove staged Expert endpoint context;

- delete RemoteTurnRoute from remote authority/pairing operations if those still use it;
- perform 2-B.5 integrated hardening;
- redesign model routing already closed in 2-B.2.

## Fixed design decisions

### 1. Turn admission cannot depend on remote discovery

AppComposition::start_turn must not perform network/model/source route resolution.

Remove the inference_routes service field from AppComposition if it has no other caller.

The turn command passed to the Vault worker contains only runtime identity/input needed by the canonical owners: session/revision/text/profile, continuation/retry, verified device id, and fixture-only/test injection where unavoidable.

A failed paired server, unavailable connector catalog, or unavailable model profile must not prevent Conversation admission.

### 2. Remove remote_route from ConversationTurnRequest

ConversationTurnRequest must not carry RemoteTurnRoute.

The internal General Conversation request must not contain model endpoint, bearer, model placement, model recipient, model consent, or source catalog.

Keep RemoteTurnRoute itself only where separate non-Conversation worker operations still require it. Do not rename it into a new conversation-specific wrapper.

The canonical command digest remains unchanged because route state was already excluded.

### 3. Source transport must not depend on Inference RemoteRoute

The root remote source reader still needs loopback server endpoint, credential, verified person/device/client pairing, and source catalog when a source actually needs it. That is not a model route.

Refactor provider source transport so ServerSourceClient no longer requires floe_inference::RemoteRoute.

Recommended adapter-private shape:

    PreparedServerSource {
        base_url
        bearer_token
        client_id
        person_id
        device_id
    }

Equivalent naming is fine.

Requirements:

- validate loopback endpoint and credential shape inside provider adapter;
- bind person/device/client identity before use;
- do not carry model purpose, model placement, external model recipient, or model consent;
- keep bearer private/redacted;
- Context/Connections never receive the bearer;
- App receives/constructs an opaque source client, not policy facts.

Using the existing saved local-server credential as adapter input is acceptable. Do not use floe_inference::RemoteRoute as the source transport contract.

### 4. Connector discovery is lazy and Connections-owned

Do not fetch /v1/connectors before Conversation admission.

For remote mail/work/logistics reads, no connector-catalog prefetch is required: the grant/source dependency already names the source.

For calendar/source enumeration, add a source-side observation method such as:

    ServerSourceClient.observe_calendar_connections(...)
      → GET /v1/connectors
      → ConnectorCatalogObservation
      → floe_connections::project_calendar_connections(...)

The exact method name may differ.

Rules:

- /v1/connectors is never fetched by model profile discovery;
- connector observation failure does not block unrelated root model/tool turns;
- catalog observation happens only when the caller actually needs source enumeration;
- Connections remains the semantic owner of catalog projection.

### 5. Model discovery and source discovery are independent

One saved server connection may support canonical model profile discovery through Inference and source reads/catalog observation through provider source adapters.

Those paths may share a credential store but may not share a route result.

The following coupling must disappear:

    /v1/inference-purposes success
      required before
    /v1/connectors/source access

and model route placement must not decide source/tool availability.

### 6. Root Expert catalog comes from Experts Directory

The root catalog must not call ConversationExperts::agent_cards() → Model::expert_eligibility() → eligible_cards(... placement ...).

Use the Experts-owned Directory/TaskCoordinator registry to list cards admitted for the exact principal and canonical purpose everyday-assistance.

Preferred implementation:

- expose a narrow TaskCoordinator/Directory catalog observation method if needed; or
- inject Directory into General Conversation composition and call list_cards.

Do not duplicate Directory eligibility rules in App.

Context tool descriptors remain merged into the root AllowedCatalog.

Definition revisions must come from the Directory entry, not App constants.

### 7. Expert execution policy stays behind the temporary delegation bridge

2-B.4 does not converge Expert model execution.

If legacy built-in Expert execution still requires Foundation/Server legacy model selection, InferencePolicyDecision, or source fallback logic, that compatibility must be prepared only when an actual delegated endpoint runs, behind:

    LegacyDelegationPort
      → TaskCoordinator
      → staged endpoint

The root run_general_turn must not eagerly construct those values.

This is temporary isolation, not a new architecture. 2-C/3-A remove the remaining bridge/domain compatibility.

### 8. Root App must not construct ConversationExperts

run_general_turn only needs Experts catalog, canonical projection, canonical model, canonical tools, and temporary delegation port.

It must not instantiate the old in-process Expert host merely to discover cards.

Any remaining ConversationExperts construction must live only inside the staged legacy Expert endpoint path.

### 9. App model policy helpers leave the root path

The following must have zero root General Conversation caller:

- Model::new;
- Model::expert_eligibility;
- policy(&Model, route);
- external_transfer_consent(... route ...);
- PersonalViewSource::server_fallback_allowed.

If these are still required solely by legacy Expert endpoints, move them into a clearly scoped Expert compatibility module/file. Do not leave them in root turn composition where they appear authoritative.

Do not create names like RootPolicyLegacyV2.

### 10. Delete dead General Conversation model bridges now

At the 2-B.4 baseline, code search shows LegacyModelPort has no production constructor.

Before deletion, inspect all actual callers.

If zero production callers remain, delete:

- engine_ports::LegacyModelPort;
- transitional_budgeted_generate;
- legacy_conversation_messages;
- contract_response;
- root-only GovernedModel;
- associated imports/tests used only by these helpers.

If a real assigned non-root caller exists, leave only that narrow compatibility surface and document the owner/stage that removes it.

Definitions with zero production callers are not a reason to postpone deletion to 2-D.

### 11. FFI/product route field is not authoritative

Stage 3 owns removal of AgentRemoteRouteDto from the outer protocol.

2-B.4 must still ensure a Conversation turn cannot use it.

In crates/bindings/ffi/src/conversion/worker.rs, the Conversation-turn conversion must stop constructing ConversationTurnRequest.remote_route.

Preferred behavior for the legacy DTO field during Stage 2:

- reject remote_route.is_some() for Conversation turns with InvalidInput; or
- if an existing wire compatibility requirement makes rejection impossible, ignore it and add a regression proving it has zero execution effect.

Reject is preferred because it prevents callers from believing an arbitrary endpoint/bearer influenced execution.

Do not remove the DTO itself in this slice.

### 12. Current root model authority remains unchanged

Do not regress 2-B.2.

The model provider may load the current saved server connection independently.

No root model selection may depend on source catalog availability.

### 13. Root source absence degrades locally

No saved/paired source connection means:

- root local tools continue to exist;
- remote Context tools return CapabilityUnavailable;
- Engine emits the existing durable unavailable Tool observation;
- root model profile selection proceeds independently;
- Conversation admission succeeds.

Do not turn absence of remote sources into a root model failure.
