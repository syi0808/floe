## Goal

Validate the complete General Conversation runtime as one system rather than as isolated slices:

~~~text
Conversation admission / continuation
  → ConversationModelProjection
  → Context authorization / provenance
  → Engine validated batch
  → InferenceService
  → Access dispatch permit / consume / revalidate
  → Provider model transport

Engine
  → ContextToolService
  → Context / Access
  → source adapter
  → ToolResult coverage
  → next projection / dispatch

Engine
  → LegacyDelegationPort
  → Experts TaskCoordinator
  → staged endpoint
~~~

The last line is an intentional temporary bridge until 2-C. 2-B.5 verifies that the bridge does not corrupt the canonical root runtime; it does not remove it.

## Operating rule: one deep audit, then stop

2-B.5 is the one planned deep audit for 2-B.

Perform the audit once against the baseline above. When a finding is fixed, run its focused regressions and the full closure suite. Do not restart a general B1-B4 audit after every fix.

Do not create another planning/status document. Record any deferred finding in the Deferred findings section of this file.

### Finding triage

**P0 — fix before 2-B closes**

- unauthorized data release or recipient/authority bypass;
- duplicate external effect or duplicate Tool/Task dispatch under recovery;
- durable validated pending work lost and replaced by a different model plan;
- stable execution/batch/step/call/task identity corruption;
- budget resurrection, double settlement, or double finalization charge;
- a cross-owner violation that makes the canonical production path unsafe.

**P1 — fix in 2-B.5 when local and bounded**

- malformed durable state not failing closed;
- missing revalidation at an existing authority fence;
- provenance/coverage loss that can make later authorization inaccurate;
- incorrect error classification that can trigger an unsafe retry/fallback;
- test/runtime seams that alter production security/authority semantics;
- accounting edge cases that do not yet duplicate an effect but can misstate durable usage.

**P2 — defer to 2-D / 2-E**

- dead compatibility with zero behavioral risk;
- naming/visibility/re-export cleanup;
- fixture ergonomics;
- migration-only public surface that is not used by the canonical production path;
- type relocation with no current authority/secret leak.

If a P2 item is found, note it here and stop touching it.

## B5-B — Security, authority, provenance, and release audit

This checkpoint validates the combined B2+B3+B4 path, especially authority changes that occur between projection, handoff, and response release.

### B5-B1 — Exact recipient and current authority

Re-run and inspect the production-backed regressions for:

- revoke before handoff → provider call count 0, usage charge 0;
- revoke after handoff before response release → provider may be called once, usage remains charged, response content is suppressed;
- exact recipient mismatch → deny;
- person/device rebinding → deny;
- removed saved connection → deny;
- external Unknown coverage → deny.

The production authority must reload current saved-connection state at every Access check.

### B5-B2 — Dependency authority can change after projection

Add integrated tests that revoke source/grant/dependency authority after projection but before model dispatch.

Required behavior:

~~~text
projection succeeds with dependency D
→ authority for D changes
→ Access admit/consume reauthorizes D
→ provider receives no unauthorized projection
~~~

Also cover revoke after provider handoff but before post-response release:

~~~text
projection + admit + consume succeed
→ provider call begins
→ dependency/grant revoked
→ provider returns
→ Access post-response revalidation denies
→ response suppressed
→ trustworthy usage remains charged
~~~

This must exercise the real CompositeDependencyResolver path, not only a unit fake.

### B5-B3 — Route-neutral processing restriction composition

Verify the B3 split did not weaken target restrictions:

- Device target + LocalOnly dependency → allowed if otherwise authorized;
- Device target + ApprovedRecipient dependency → denied;
- External target + LocalOnly dependency → denied;
- External target + exact ApprovedRecipient + matching categories → allowed;
- External target + wrong recipient/category → denied.

For Auto model selection after a Tool result, verify that a target incompatible with the ToolResult dependency never receives the data.

Fail-closed is acceptable. Do not add a fallback that converts a generic Access PolicyDenied into a different target unless the authorization contract can distinguish that case safely.

### B5-B4 — Historical provenance and freshness

Exercise the full persisted history path:

1. complete a turn whose answer depends on source-backed coverage;
2. persist the terminal coverage;
3. start a later turn;
4. reauthorize historical derived content;
5. revoke or stale the source;
6. project again.

Required behavior:

- fresh authorized derived history is retained;
- stale/revoked/Unknown derived history is dropped;
- the Person's own historical User text remains;
- dropped history contributes no dependency;
- retained history dependency reaches AuthorizedModelProjection.coverage;
- the answering ValidatedModelBatch persists that coverage;
- a later turn cannot reuse the derived answer after authority is gone.

### B5-B5 — Tool result provenance

## B5-C — Recovery, replay, and stable identity audit

### B5-C1 — Validated batch before side effects

For a model batch containing Tool/Delegate/Answer combinations:

- invalid whole batch dispatches zero Tool/Task side effects;
- ValidatedBatch is durable before side-effect execution;
- pinned Tool/Agent revisions are verified on resume;
- projection_coverage is part of full batch equality.

### B5-C2 — Crash-point matrix

Cover these durable crash points:

1. ModelResult before ValidatedBatch;
2. ValidatedBatch before first BatchProgress;
3. resumed ValidatedBatch before initial resume cursor;
4. ToolIntent before ToolResult;
5. ToolResult before cursor advance;
6. DelegationIntent before DelegationResult;
7. DelegationResult before cursor advance;
8. Preamble cursor before in-memory push;
9. validated Answer batch before output commit where the existing recovery contract permits the state.

Required outcomes:

- no model re-plan when a durable pending batch exists;
- no duplicate Tool/Task dispatch;
- replayed Tool/Task result binds the exact call/task and ordinal;
- corrupt/mismatched state fails with StorageUnavailable/Conflict according to the existing durable contract, never model correction;
- pending work is not silently normalized to cursor zero.

### B5-C3 — Cross-run continuation

Re-run and extend where needed:

- child crash before takeover preserves parent pending batch/cursor;
- batch-only child does not supersede parent;
- exact child batch+cursor takeover supersedes parent;
- mismatch in batch, cursor, or projection_coverage fails closed;
- orphan resumed child fails closed;
- fresh child plan cannot skip parent pending work.

Include one real Vault multi-run regression, not only pure reconciliation tests.

### B5-C4 — Stable identity

For Tool and Delegation verify:

~~~text
execution_id + batch_id + ordinal + kind
→ stable InvocationKey
→ stable call_id / task_id
~~~

The same durable batch resumed multiple times must produce exactly the same identities. A different ordinal/kind must not collide.

## B5-D — Model accounting and finalization audit

### B5-D1 — One attempt ID end to end

For every canonical root model attempt:

~~~text
Engine ModelIntent.attempt_id
== ModelRequest.attempt_id
== CanonicalModelRequest.attempt_id
== provider-observed attempt_id
== ModelResponse.attempt_id
== ModelResult.attempt_id
~~~

A host correction creates a new attempt ID; it must not reuse the failed attempt.

### B5-D2 — Charge semantics

Required matrix:

**Before handoff**

- invalid request / profile unavailable / Access denied / cancellation before consume:
  - provider calls 0;
  - dispatched attempts 0;
  - usage charge 0.

**After handoff, unknown usage**

- transport timeout/error after mark_dispatched:
  - one unknown estimate charged;
  - Engine journals that delta;
  - restart does not resurrect it.

**After handoff, trustworthy usage**

- valid response:
  - settle actual usage exactly once;
- invalid provider payload with trustworthy usage:
  - actual usage remains charged once;
- post-response Access denial:
  - actual usage remains charged once;
  - content suppressed.

### B5-D3 — Auto fallback accounting

When Auto tries candidate A, A fails after dispatch, and candidate B succeeds:

- A and B each use a fresh Access permit/fence;
- A contributes exactly one unknown/known charge according to its failure point;
- B contributes exactly one actual settlement;
- there is no reuse of A's budget attempt;
- final ModelResult durable usage equals the aggregate scope delta expected by recovery.

Admission denial must not be bypassed by fallback.

### B5-D4 — Continuation accounting

Across parent → child continuation:

- completed iterations accumulate exactly once;
- prior usage initializes the child budget exactly once;
- failed-attempt usage is not lost;
- child takeover does not duplicate parent usage;
- resuming a pending validated batch performs no model call and adds no model-attempt usage until a real new model attempt occurs.

### B5-D5 — Finalization reserve

Audit the BudgetExceeded/Stalled finalization path:

- work partition cannot consume the finalization reserve;
- only the root scope can open one finalization scope;
- finalization model attempt uses the same canonical ModelPort;
- successful finalization settles once;
- dispatched failed finalization charges once;
- no second finalization attempt is created from the same exhausted run;
- ConsentRequired/PolicyDenied/CapabilityUnavailable barriers do not trigger unsafe finalization when the existing finalization barrier forbids it;
- finalization coverage includes its answering projection and retained independent observations.

Add an integrated regression that would fail if reserve or usage is double charged.

## B5-E — Ownership and secret-boundary audit

### B5-E1 — Canonical owner rules

Verify production root behavior, not only dependency graph declarations:

- App composes, but does not choose model/source/access policy;
- Conversation owns Session/Run/transcript/continuation;
- Context owns projection/tool/source semantics and provenance;
- Inference owns profile/routing/attempt/usage;
- Access owns exact recipient and dispatch fences;
- Provider owns transport and credential use;
- Experts owns catalog/Task identity and lifecycle.

A direct dependency is not automatically a violation; business judgment in the wrong owner is.

### B5-E2 — Canonical secret boundary

Inspect canonical production types and Debug/Serialize surfaces:

- AuthorizedModelProjection;
- ModelDispatchRequest;
- ModelProfile / PreparedModelProfile;
- CanonicalModelRequest;
- ContextToolService inputs/results;
- ConversationTurnRequest.

They must not expose raw bearer/token/arbitrary endpoint to Conversation, Context, Access, or product turn input.

Credential values may exist only in provider/credential composition state.

### B5-E3 — Legacy/public secret types

The repository still has compatibility types such as SavedServerConnection, RemoteRoute, and legacy ModelTransport-related values.

Classify them by actual caller:

- if a raw secret-bearing type crosses the canonical root execution contract or is reachable from Conversation/Context/Access business APIs → P0/P1, fix in 2-B.5;
- if it is only adapter composition, staged legacy Expert/domain compatibility, outer remote authority/pairing, or a migration-only public re-export → record as P2 for 2-D/2-E/Stage 3.

Do not move a type merely to make grep output pretty.

### B5-E4 — Test seams must not change production authority semantics

Audit test-only behavior embedded in production code, including keychain hermeticity seams.

A test seam is acceptable only when it cannot weaken production authorization, redirect credentials, skip a production fence, or change product behavior under an ordinary production environment.

If a seam such as an environment variable changes production credential lookup semantics, either:

- replace it with injected test storage/adapter state; or
- prove it is unreachable in production builds through compile-time gating.

Do not leave runtime security/authority behavior controlled by a test-only environment convention.

### B5-E5 — Architecture boundaries

Run the architecture checker and inspect the actual call path for false negatives.

In particular verify:

- Inference → concrete Context = 0;
- Context → Inference = 0;
- Access → agent runtime/Conversation = 0;
- Provider canonical model path does not call Access/Context business policy;
- App root path contains no Foundation/Server selection branch;
- root Tool availability is independent from model profile;
- pre-turn App admission does not query provider/model/source network state.
