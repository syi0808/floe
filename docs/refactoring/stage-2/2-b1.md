# 2-B.1 Final P0 — Cross-run Resume Lineage

**Status: complete / frozen**

**Code baseline reviewed:** `c25f828e43f56e70fa542d4a38482835e22cbd04`

This document is the execution plan for the last 2-B.1 P0. It is intentionally narrow. Do not start 2-B.2, do not reopen single-journal recovery, and do not redesign Engine/Inference/Access while executing this plan.

## Goal

Guarantee that a continuation child can take over a parent's pending `ValidatedModelBatch + BatchCursor` only after the child durably records the **exact same batch and exact starting cursor**.

A newer Run is not enough to supersede older pending work.

The required invariant is:

```text
parent pending = (batch B, cursor C)

child journal:
  ValidatedBatch(B)
  BatchProgress(C)
        ↓
durable takeover confirmed

before both records exist:
  parent (B, C) remains authoritative
```

If the child records a different batch/cursor, starts a fresh model plan before takeover, or resumes without any parent pending state, recovery fails closed with `AgentFailure::StorageUnavailable`.

## Why this remains P0

Current `continuation()` in `crates/modules/conversation/src/application/coordinator.rs` projects every run independently and then keeps live state only from the newest run:

```text
older pending batch
→ newer child exists
→ older pending state discarded
```

That is unsafe when the child:

1. crashes before Engine writes its resume records;
2. writes only the resumed `ValidatedBatch` but crashes before the initial `BatchProgress`;
3. writes a different resumed batch/cursor;
4. starts a fresh `ModelIntent` without first taking over the parent pending batch.

Any of these can lose a previously validated side-effect plan and allow a later model re-plan.

## Existing behavior to preserve

Do not change these already-correct contracts:

- Engine resume keeps the original `execution_id`.
- Engine verifies pinned revisions before executing a resumed batch.
- Engine re-journals resume state in this order:
  1. `JournalEvent::ValidatedBatch { batch }`
  2. `JournalEvent::BatchProgress { cursor }`
  3. execute from `cursor.next_step_index`
- Single-journal recovery already binds Tool/Delegation intent/result/cursor to the validated step and stable identity.
- Model usage, completed iterations, replay and typed exchanges remain cumulative across the continuation chain.
- Public `ContinuationSnapshot` stays the runtime handoff shape unless implementation evidence proves a contract change is unavoidable.

## Implementation plan

### 1. Add private journal-origin metadata to recovery projection

**Primary file:** `crates/modules/conversation/src/application/recovery.rs`

Extend private `JournalProjection` with enough metadata to distinguish how this run began. Keep it private to Conversation; do not add a new public wire/storage field.

Recommended shape:

```rust
enum JournalLineage {
    Empty,
    Fresh,
    ResumeBatchOnly {
        batch: ValidatedModelBatch,
    },
    ResumeClaimed {
        batch: ValidatedModelBatch,
        cursor: BatchCursor,
    },
}
```

Equivalent naming is fine. The semantics are required.

State transitions:

- initial state → `Empty`;
- first local `ModelIntent` → `Fresh`;
- leading `ValidatedBatch` with no local attempt, currently recognized as `fresh == false` → `ResumeBatchOnly`;
- the first `BatchProgress` for that leading resumed batch → `ResumeClaimed { exact batch, exact cursor }`.

The lineage value remains `ResumeClaimed` even if that run later completes the resumed batch and creates fresh model attempts.

### 2. Do not treat batch-only re-journaling as takeover

A crash can occur between:

```text
ValidatedBatch(B)
<crash>
BatchProgress(C)
```

Therefore `ResumeBatchOnly` is **not** durable takeover.

For a run in `ResumeBatchOnly`:

- no ToolIntent;
- no DelegationIntent;
- no ModelIntent;
- no result/checkpoint that assumes the batch started;

may be accepted before its initial `BatchProgress`.

If such activity appears before the initial cursor, return `StorageUnavailable`.

This closes the local ambiguity where `cursor.unwrap_or(0)` could otherwise make an unclaimed resumed batch look as if it started at ordinal 0.

### 3. Record the exact initial resume cursor

When the first `BatchProgress` transitions `ResumeBatchOnly → ResumeClaimed`:

- require `cursor.batch_id == batch.batch_id`;
- validate the cursor against the batch length using the existing recovery rules;
- store the exact `BatchCursor` in `JournalLineage::ResumeClaimed`.

Do not normalize the cursor to zero and do not derive a new batch identity.

### 4. Replace “newest run wins” with explicit lineage reconciliation

**Primary file:** `crates/modules/conversation/src/application/coordinator.rs`

In `continuation()`, replace the current assumption:

> an older pending batch was superseded the moment a newer run continued past it

with explicit chronological reconciliation.

Maintain a private carried live state:

```rust
Option<(ValidatedModelBatch, BatchCursor)>
```

or a small private struct.

For every projected run from oldest → newest, apply the following state table.

#### No inherited parent pending

- child `Empty` → allowed; current projected pending becomes the next carried state.
- child `Fresh` → allowed; current projected pending becomes the next carried state.
- child `ResumeBatchOnly` → `StorageUnavailable` (orphan resume).
- child `ResumeClaimed` → `StorageUnavailable` (orphan resume).

#### Parent pending = (B, C)

- child `Empty` → child has not taken over; carry parent `(B, C)` forward.
- child `ResumeBatchOnly(B)` → require exact batch equality; takeover is incomplete, so carry parent `(B, C)` forward.
- child `ResumeBatchOnly(B2 != B)` → `StorageUnavailable`.
- child `ResumeClaimed(B, C)` → exact takeover confirmed; from this point use the child's projected live pending/cursor as the new carried state.
- child `ResumeClaimed` with batch or cursor mismatch → `StorageUnavailable`.
- child `Fresh` → `StorageUnavailable`; a fresh model plan cannot skip parent pending work.

Use `ValidatedModelBatch::Eq` and `BatchCursor::Eq`; do not compare only batch IDs.

At the end of the chain, return the carried state as `ContinuationSnapshot.pending_batch/batch_cursor`.

### 5. Keep cumulative state aggregation unchanged

The lineage fix must not regress existing aggregation:

- transcript/history projection;
- deduplicated Tool/Delegation exchanges;
- replay receipts;
- completed iteration total;
- model usage total;
- continuation generation/level validation.

Extract a small private reconciliation helper if that keeps `continuation()` readable, but do not create a new architectural service or public contract.

### 6. Engine should normally require no production change

**Reference:** `crates/runtime/agent/src/engine.rs::Engine::run`

Engine already writes:

```text
ValidatedBatch(resume.validated_batch)
BatchProgress(resume.cursor)
```

before executing resumed steps.

Do not change Engine unless a regression proves the current journal order is insufficient. The owner of this P0 is Conversation cross-run recovery, not a new Engine protocol.

## Failure semantics

Lineage corruption is durable storage inconsistency:

```rust
Err(AgentFailure::StorageUnavailable)
```

Do not map it to `InvalidInput`, `Conflict`, or a model correction.

A child that simply has no resume evidence yet is not corrupt; it means takeover did not happen and the parent's pending state remains authoritative.
