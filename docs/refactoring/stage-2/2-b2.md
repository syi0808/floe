# 2-B.2 — Canonical Model Vertical Slice

**Status: residual P0 active — vertical cutover otherwise complete**

**Code baseline reviewed:** `dd1b37387157c30ab027bd4619742bf5bd8a0d0e`

This document is the main execution plan for 2-B.2. The vertical cutover is implemented, but final closure is temporarily gated by the [current-recipient authority P0](2-b2-current-authority.md). Do not start 2-B.3 until that residual plan is complete.

## Goal

Replace the root General Conversation model path with one canonical owner chain:

```text
Agent Engine
  → InferenceService : ModelPort
  → Access model-dispatch admission / consume fence
  → prepared Provider transport
  → Access post-response revalidation
  → canonical ModelResponse
```

At the end of 2-B.2:

- the root Manager does not execute through `LegacyModelPort`;
- App does not choose Foundation vs Server for the root Manager attempt;
- Inference owns profile selection, route planning, transport retry/fallback and model budget settlement;
- Access owns exact-recipient dispatch authority;
- Provider owns transport and credentials;
- Engine, Inference and Provider use the same model `attempt_id`;
- no raw bearer token or arbitrary model endpoint crosses Inference's public boundary.

This is a vertical production cutover, not another foundation-only slice.

## Scope boundary

### In scope

- Conversation admission must stop requiring a model placement resolved before the Run is admitted.
- Access gets a model-specific dispatch permit/fence distinct from storage `ReleasePermit`.
- Inference gets the canonical root `ModelPort` implementation.
- Provider adapters expose non-secret model profiles and an opaque prepared transport capability.
- Canonical provider requests consume the immutable `ContextEnvelope` / catalog rather than old `InferencePolicyDecision + AgentContext` authorization.
- General Conversation root wiring moves from `LegacyModelPort` to `InferenceService`.
- Canonical model profile discovery no longer fetches `/v1/connectors`.

### Explicitly out of scope

Do not start:

- 2-B.3 Context-owned model projection;
- `ContextToolService`;
- `LegacyToolPort` removal;
- `LegacyDelegationPort` removal;
- App `ConversationCapabilities` cleanup;
- built-in Expert / Schedule model-host convergence;
- `run_calendar_agent_turn` / `CalendarTurn` convergence;
- Stage 3 FFI/Flutter DTO cleanup.

The legacy App `Model` enum and old `ModelTransport` may remain for **non-root compatibility callers** during this slice. They must no longer be authoritative for the root Manager model call.

## Current production path

Today the root path still does this:

```text
AppComposition::start_turn
  → HostInferenceRoutes::resolve(caller)
  → ConversationTurnRequest.remote_route

run_general_turn
  → Model::new(remote_route)          # App chooses Foundation / Server
  → policy(&model, remote_route)
  → TransitionalModelProjection
  → LegacyModelPort
  → RootModel
  → old Conversation ModelRunner
  → floe-inference::ModelTransport
  → FoundationModelRunner / ServerModelRunner
```

The same pre-resolved App model also affects transitional Tool/Expert availability. 2-B.2 removes it only from the **root Manager model execution authority**; 2-B.3 and Stage 3 clean the remaining source/Expert/product-boundary coupling.

## Fixed design decisions

### 1. Admission records profile intent, not resolved placement

A model route is selected after admission. Therefore Conversation/Vault must not require `device_local` or `remote` before creating the Run.

Use the existing `ProfileSelection` as the durable execution preference.

Replace the current placement-derived chain:

```text
TurnRequest.execution_profile
→ parse_execution_profile()
→ VaultConversationRunRecord.model_placement
→ execution_profile(record.model_placement)
```

with Conversation-owned profile intent.

Preferred shape:

- remove `TurnRequest.execution_profile`;
- carry `ProfileSelection` through `TurnAdmissionRequest` / `RunReceipt` as needed for continuation consistency;
- replace Vault run-record `model_placement` with the admitted profile preference;
- continuation lineage compares the admitted profile preference, not a model route result.

Do not persist endpoint, bearer, provider recipient or Foundation/Server choice in the Run admission record.

Old local-development run payloads do not require a compatibility decoder. Do not bump schema numbers merely for this refactor, and never auto-delete/reset user data on an access error.

### 2. Projection remains route-free

`AuthorizedModelProjection` remains exactly the input-authorization object:

- projection ref/revision;
- immutable `ContextEnvelope`;
- dependency coverage;
- input data classes.

Do not add:

- recipient;
- endpoint;
- bearer/credential handle;
- provider name;
- resolved placement.

2-B.3 will replace `TransitionalModelProjection`; 2-B.2 must keep it usable without moving route policy into it.

### 3. Access owns model dispatch authority

Do not reuse or rename storage `ReleasePermit`.

Add a distinct Access application contract, suggested location:

```text
crates/modules/access/src/application/model_dispatch.rs
crates/modules/access/src/ports/model_dispatch.rs
```

Equivalent file naming is acceptable; ownership is not.

Because Access must not depend on `floe-agent-contract`, model dispatch types use only kernel/context/execution values.

Recommended contract:

```rust
enum ModelDispatchTarget {
    Device,
    External { recipient: String },
}

struct ModelDispatchRequest {
    person_id: PersonId,
    projection_ref: Uuid,
    projection_revision: u64,
    coverage: DependencyCoverage,
    input_data_classes: Vec<DataClass>,
    purpose: String,
    consumer: String,
    target: ModelDispatchTarget,
    deadline: Instant,
    cancellation: Cancellation,
}
```

Add:

- `ModelDispatchPermit` — admitted but not yet handed off;
- `ModelDispatchFence` — consumed immediately before transport and retained for post-response revalidation;
- a narrow Access-owned recipient-authority port that reports current exact recipient authority/consent without exposing credentials.

The exact names may differ. The separation may not.

### 4. Source/grant freshness and recipient restriction are separate checks

Reuse the existing Access `DependencyResolver` for current dependency/grant/source reauthorization.

Map the selected dispatch target to the existing placement constraint only for dependency reauthorization:

- `Device` → `[ModelPlacement::DeviceLocal]`;
- `External` → `[ModelPlacement::Remote]`.

Then independently enforce each dependency's `ProcessingRestriction` for external dispatch:

- `LocalOnly` → external dispatch denied;
- `ApprovedRecipient { recipient, categories }` → recipient must be an exact string match;
- every dependency category must be admitted by the approved-recipient category set.

Do not infer an external recipient from placement.

For an external target:

- `DependencyCoverage::Unknown` is not releasable and must fail closed;
- `Dependent` coverage must reauthorize every dependency and exact processing restriction;
- `Independent` may proceed only when data-class and exact-recipient authority permit it.

A Device target may keep local degraded/Unknown behavior because no external release occurs, but dependent coverage still reauthorizes current authority when dependencies are known.

Never send `DataClass::Credential` or `DataClass::DeviceOnlyRaw` to a model. Until a separate bounded-sensitive contract exists, external `HighlySensitive` model dispatch fails closed.

### 5. Permit lifecycle has three authority points

The Access sequence is:

```text
admit_model_dispatch(...)
    ↓
ModelDispatchPermit

consume_model_dispatch(permit)
    # immediately before provider handoff
    # repeats current authority/dependency/recipient checks
    ↓
ModelDispatchFence

provider call
    ↓
revalidate_model_dispatch(&fence)
    # after response, before response leaves Inference
```

Revocation between any two stages must prevent data release or response release.

### 6. Inference may depend on Access; Access may not depend on agent contracts

The target architecture already permits:

```text
floe-inference → floe-access
```

Add the dependency to `crates/modules/inference/Cargo.toml`.

Do not invert it by importing `ModelRequest`, `ProjectionRef` or other agent types into Access.

### 7. Provider profile observation is non-secret

The canonical Inference path sees only `ModelProfile` / `PlannedRoute` facts:

- profile id;
- purpose;
- consumer;
- execution location;
- data recipient;
- capabilities;
- availability.

User consent is not a provider-profile fact. Remove or stop using `ModelProfile.external_transfer_consent` as a routing authorization. Access owns that decision.

Adapt the device-only Knowledge/Learner profile code if this field is removed; do not preserve a fake consent boolean just for compatibility.

### 8. Auto profile choice belongs to Inference

Explicit selection:

- profile id must match exactly;
- missing/unavailable/incompatible explicit profile is terminal for that request;
- never silently fall back.

Auto selection:

- deterministic local-first policy owned by Inference;
- device execution + device recipient preferred;
- gateway/local-server execution with device recipient next;
- external recipient only after local candidates are unavailable/ineligible and Access admits that exact recipient;
- ambiguity at the same policy rank fails closed rather than choosing an arbitrary profile.

Transport fallback is Inference-owned. A fallback to a different target requires a fresh Access permit/fence for that target.

Do not let App select Foundation/Server to implement Auto.

### 9. Provider transport capability is opaque

Do not create a public route bundle containing:

```text
base_url + bearer_token + recipient
```

for the canonical path.

Add an Inference-owned provider port that returns non-secret profile observations paired with an **opaque prepared transport capability** whose secret fields stay in the provider adapter.

One acceptable shape is:

```rust
trait ModelProvider: Sync {
    type Prepared: PreparedModelTransport;

    fn observe_profiles(...) -> ...Vec<PreparedModelProfile<Self::Prepared>>...;
}

trait PreparedModelTransport: Sync {
    fn generate(...) -> ...;
}
```

The concrete provider adapter may use a private enum for Foundation vs Server. Inference may choose a prepared profile, but may not inspect its credential/endpoint internals.

Do not call the new port `ModelTransportV2` or create parallel version naming.

### 10. Canonical provider request uses the envelope/catalog, not legacy policy/context

Do not move the old `ModelTransportRequest` construction into `InferenceService`.

The canonical provider request should contain only what an already-authorized attempt needs, for example:

- `attempt_id`;
- immutable `ContextEnvelope`;
- bounded `AllowedCatalog` for tool/Expert wire declarations and revision mapping;
- input data classes when the provider wire must audit them;
- remaining token/cost allowance;
- max output bytes;
- deadline/cancellation.

It must not contain:

- `InferencePolicyDecision`;
- mutable/legacy `AgentContext`;
- duplicate rendered prompt when the envelope already owns instructions;
- Session/Task;
- mutable ledger;
- bearer/base URL.

Provider adapters map wire tool/Expert calls back to canonical agent `ModelStep` with the exact catalog definition revision. Engine remains the whole-batch grammar owner.

The old `floe_inference::ModelTransport` may remain temporarily for legacy Expert/Learner/domain callers, but the root General Conversation path must not adapt back into it.

### 11. Canonical model discovery never fetches connector catalog

Split `crates/adapters/providers/src/models/server.rs::resolve_remote_model_route`.

The canonical model profile path:

```text
saved private connection
→ /v1/inference-purposes
→ non-secret model profile observation
```

must not call `/v1/connectors`.

`/v1/connectors` remains a Connections/source concern and may stay in the temporary legacy source/Expert route path until 2-B.3 / Stage 3.

Add a regression that counts canonical model-profile HTTP calls and proves `/v1/connectors == 0`.

### 12. One logical attempt ID end to end

`crates/modules/inference/src/application/attempt.rs::AttemptLifecycle::start` currently creates a new UUID.

Change the canonical attempt lifecycle so it receives the caller's `ModelRequest.attempt_id`.

The identity chain must be:

```text
Engine ModelIntent.attempt_id
  == Inference logical attempt id
  == Provider request attempt_id
  == returned ModelResponse.attempt_id
```

Legacy callers that still need a generated id may mint it at their own compatibility boundary; `AttemptLifecycle` itself must not silently replace a canonical caller id.

Do not create a second durable attempt ledger just for 2-B.2. The Conversation Engine journal remains the durable Run-level ModelIntent/ModelResult record. Inference owns the live dispatch/usage lifecycle.

### 13. Inference is the single model budget owner

The canonical `InferenceService::generate` uses `ExecutionScope::budget()` directly.

Do not create a detached `UsageLedger`.

Required order:

```text
validate canonical ModelRequest
→ observe profiles
→ plan candidate route
→ Access admit
→ reserve scope budget
→ Access consume fence
→ mark budget attempt dispatched
→ provider dispatch
→ settle actual usage when trustworthy
→ Access post-response revalidate
→ return canonical ModelResponse
```

Rules:

- Access denied before handoff → provider calls 0, budget charge 0.
- Failure after `mark_dispatched` with no trustworthy usage → dropping the attempt charges the existing unknown estimate.
- Successful transport usage is settled exactly once.
- If post-response Access revalidation fails, usage stays charged and response content is discarded.
- If provider response is invalid after usage is known, usage stays charged and Engine sees the failure; Engine's existing budget-delta failure journal preserves it.
- Engine does not also settle successful usage.

The transitional `transitional_budgeted_generate` remains only behind `LegacyModelPort` compatibility and is no longer in the root production path.

### 14. Purpose/consumer are canonical owner values

The current code mixes `everyday-assistance` and `everyday_assistance`.

Use one canonical model purpose compatible with the server purpose contract:

```text
everyday_assistance
```

and the existing Conversation consumer:

```text
conversation.root
```

Do not let App invent a different purpose through `policy(&model, route)`.

The root `ModelRequest.purpose`, envelope scoped purpose, Inference `ModelPurpose`, Access dispatch request and provider wire purpose must agree.

### 15. Root cutover does not pull Expert/Tool cleanup forward

In `run_general_turn`:

keep for now:

- `TransitionalModelProjection` — removed in 2-B.3;
- `LegacyToolPort` — removed in 2-B.3;
- `LegacyDelegationPort` — removed in 2-C;
- legacy `Model` / `ExpertModelHost` where still needed by transitional Tool/Expert paths;
- `RemoteTurnRoute` where still needed by legacy source/Expert paths.

replace only the root model wiring:

```text
LegacyModelPort
    ↓
InferenceService
```

The remaining App `Model` object must be clearly non-authoritative for the root Manager. Do not rename it merely to hide legacy ownership.
