# 3-C — Protocol and FFI Contract Cutover

**Status: pending · scope fixed from Stage 3 baseline review**

**Baseline used for scope:** `39263a1339d0519b78a20680c0eea73506ff6d6f`

## Goal

Make product wire contracts express user/connection intent rather than internal model/source execution topology.

3-C defines the final Rust product contract and FFI conversion. 3-D migrates Flutter/native/server callers to it. 3-E deletes caller-zero compatibility.

## Existing canonical Conversation contract

Do not invent a third Conversation DTO.

The current canonical command already exists in
`crates/bindings/protocol/src/dto/commands.rs`:

~~~text
AppCommandDto::ConversationStartTurn {
  session_id
  expected_revision
  text
  mode
  profile
  retry_of
}
~~~

It intentionally does not carry person/device injection, endpoint, bearer or model route. The verified AppHost caller supplies person/device identity.

3-C preserves this shape unless a concrete owner requirement discovered after 3-A/3-B requires a bounded change.

## C1 — remove duplicate Conversation worker contract

The old AgentVault path still contains:

- `AgentVaultActionDto::ConversationTurn`;
- `AgentConversationTurnRequestDto`;
- FFI `conversation_turn_request` conversion;
- a deprecated `remote_route` field that is already rejected for Conversation execution.

Revalidate real product callers. Once zero, remove the duplicate ConversationTurn worker/wire path rather than maintaining two product contracts.

Tests proving a stale `remote_route` is rejected on the canonical app wire may remain as negative unknown-field tests without preserving the deprecated DTO.

## C2 — split `AgentRemoteRouteDto` by owner intent

`AgentRemoteRouteDto` currently mixes:

- base URL;
- bearer token;
- model purpose/placement/consent fields;
- pairing identity;
- calendar connection/source state.

It is used by remote authority, pairing and remote grant operations even though those are Connections/Access concerns.

Do not replace it with another “route” DTO containing the same bundle.

Use existing owner concepts where possible:

- Connections `PairingIdentity` / pairing attempt/status;
- Access `RemotePairingIdentity`;
- stable connection/grant/source references;
- reviewed producer/issuer identities.

If initial pairing must name an address before a durable connection exists, model that as a bounded connection/pairing field. It must not carry model purpose, model recipient policy or unrelated source catalog fields.

## C3 — secret boundary

Product requests into Rust must not supply an already-saved server bearer for model/source execution.

The current macOS Flutter Keychain bridge and Rust provider adapter use the same Floe-owned saved-connection slot. After pairing/credential persistence, Rust adapters should read the current saved connection through their store and bind it to verified person/device identity.

Do not move Keychain parsing into protocol conversion.

Pairing responses may legitimately contain newly issued credential material long enough to persist it; that is connection setup, not permission to pass the bearer back through every protected operation.

## C4 — FFI conversion

Primary files include:

- `crates/bindings/protocol/src/dto/agent.rs`;
- `crates/bindings/protocol/src/dto/commands.rs`;
- `crates/bindings/ffi/src/conversion/worker.rs`;
- `crates/bindings/ffi/src/app_wire.rs`;
- `crates/bindings/ffi/src/abi.rs`;
- `crates/bindings/ffi/include/floe_ffi.h`.

Keep conversion responsible for:

- schema and structural validation;
- ID parsing;
- bounded text/collection validation;
- enum/DTO translation;
- failure-envelope translation.

Do not put into FFI:

- route selection;
- grant authorization;
- recipient consent;
- provider fallback;
- source eligibility;
- retry/usage policy.

## C5 — ABI coexistence during caller migration

The repository currently exposes both:

- `floe_core_command_v2/query_v2/events_v2`;
- `floe_core_agent_vault` and older domain entry points.

Do not delete an ABI merely because its name contains `v2` or `agent_vault`.

Classify operations by final product meaning:

- canonical owner-intent APIs stay;
- internal worker-shaped compatibility migrates in 3-C/3-D and deletes in 3-E;
- genuine domain APIs may remain if their request is already a stable product contract.

Do not increment schema numbers solely for this refactor; AGENTS.md keeps app wire 2 unless semantics require otherwise.

## Acceptance

3-C is complete when:

- canonical Conversation product input remains intent-only;
- duplicate AgentVault ConversationTurn path has a documented zero-caller migration state;
- no product model/source execution request contains raw endpoint/bearer/model route;
- pairing/grant operations speak Connections/Access intent rather than Inference route topology;
- `AgentRemoteRouteDto` has no role in the final contract;
- FFI performs structural conversion only;
- one source snapshot defines the Rust protocol/FFI contract that 3-D callers will consume;
- temporary old ABI/DTO shapes retained for 3-D are explicitly enumerated, not silently preserved.

On completion, mark 3-C complete/frozen, update the Stage 3 checkpoint to 3-D and stop.
