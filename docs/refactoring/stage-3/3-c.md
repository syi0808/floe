# 3-C — Protocol and FFI Contract Cutover

**Status: complete · frozen**

**Execution baseline:** `25b1ccf0f4a4a51d3ef9493a4b510143a4c08f31` (`refactor: close Stage 3-B AppHost composition`)

**Actual execution baseline:** `c2f6647cac94a451f40b161b0337bedcc3117a0a` (latest fetched `origin/main` at execution start; see the Agent report).

This document is the authoritative execution plan for 3-C.

## Goal

Define and implement the final **Rust protocol + FFI product contracts** for the Stage 3 connection/pairing and remote-access flows.

3-C removes product-wire model/source topology from those flows. It does **not** migrate Flutter callers yet; 3-D consumes the Rust contract frozen here.

After 3-C:

- canonical Conversation stays on `command_v2/query_v2/events_v2` with the existing intent-only DTO;
- the obsolete AgentVault ConversationTurn wire is gone;
- `AgentRemoteRouteDto` is gone from the final Rust protocol;
- initial pairing may name a bounded loopback setup endpoint because no durable connection exists yet;
- pairing requests do not carry bearer/model-purpose/consent/source-catalog fields;
- after pairing, authority/grant operations receive no endpoint, bearer or pairing bundle from the product caller;
- post-pairing protected operations resolve the current saved connection inside Rust and bind it to verified `CallerContext` person/device identity;
- pairing/Connections meaning is separate from Access grant meaning;
- FFI does structural validation/conversion only;
- Rust protocol/FFI intentionally no longer accepts the old Flutter route-shaped requests. 3-D updates those callers.

This is a **direct contract replacement**, not a compatibility-version exercise.

---

Do not reopen or weaken:

- Stage 2 Conversation Run/replay/recovery semantics;
- Stage 2 exact recipient, current-authority and post-response revalidation;
- Stage 2 durable side-effect and cancellation invariants;
- 3-A canonical Inference execution;
- 3-A canonical Foundation transport;

- 3-B provider-owned current credential loading/admission;
- 3-B canonical AppHost `ConversationCommands` / `ConversationQueries` / `ConversationEvents`;
- Connections pairing identity/challenge/report validation;
- Access producer pinning, remote grant scope, authority and revocation semantics;
- provider-owned credential redaction.

Do not route product connection operations through Inference merely because the old DTO was named a route.

# Fixed 3-C design

## 1. Canonical Conversation contract is already final

Keep:

~~~text
AppCommandDto::ConversationStartTurn {
  session_id
  expected_revision
  text
  mode
  profile
  retry_of
}
~~~

Do not add:

- `person_id`;
- `device_id`;
- endpoint/base URL;
- bearer/token;
- `remote_route`;
- provider placement;
- Access flags.

Verified person/device remain `AppHost::request(...)` → `CallerContext`.

### Important distinction

The obsolete **wire** path may be deleted:

~~~text
AgentVaultActionDto::ConversationTurn
AgentConversationTurnRequestDto
conversation_turn_request(...) FFI conversion
~~~

The internal:

~~~text
WorkerAction::ConversationTurn
VaultBridge::start_conversation
ConversationTurnRequest
~~~

is still the canonical App runtime machinery behind `ConversationCommands` and must remain.

Likewise, `AgentVaultActionDto::ConversationSession` is still used by current Flutter session start/resume/load/recover code. Do not delete it as collateral damage.

## 2. Product identity must come from AppHost

3-B made current-connection admission require exact verified person/device identity.

The old `floe_core_agent_vault` request has a caller-supplied `person_id` but no trusted host device identity. It cannot be the final security boundary for post-pairing protected operations.

New/final connection and remote-access FFI paths must:

~~~text
request_id
  → AppHost::request(request_id)
  → CallerContext { verified person, verified device, runtime epoch }
  → typed App service
  → owner
~~~

A product request must not supply an alternate person/device that Rust then trusts.

If a DTO contains an identity that is intrinsically part of a signed producer/challenge/source reference, that identity is evidence to validate, not a replacement for `CallerContext`.

## 3. Pairing setup and saved connection are different states

### Before pairing

No saved bearer exists yet.

The user-entered loopback server address is legitimate **connection-setup intent**. It is not a model route.

A pairing setup target therefore contains only the minimum needed to reach the pending server, conceptually:

~~~rust
pub struct PairingTargetDto {
    pub base_url: String,
}
~~~

The exact type name may differ, but it must not contain:

- bearer/token;
- model purpose;
- model placement;
- external-transfer consent;
- recipient;
- connector/calendar catalog;
- duplicate person/device.

The provider `HttpRemoteControl` continues to validate the endpoint as an allowed loopback setup target.

### After pairing

Flutter persists the approved connection to the Floe-owned Keychain slot.

All later protected authority/grant operations use:

~~~text
CurrentSavedConnectionStore
  → provider-owned exact person/device admission
  → opaque authority/source transport
~~~

The caller sends owner intent only.

## 4. Pairing identity is derived, not route-carried

For pairing confirm/status/finalize:

- `person_id` = verified `CallerContext.person_id`;
- `device_id` = verified `CallerContext.device_id`;
- `client_id` / pairing identity = the exact pending `pairing_id` named by the signed challenge/operation;
- endpoint = bounded pairing setup target.

Connections remains responsible for validating that challenge/status/report identity is exact.

Do not add a generic `pairing: { person_id, device_id, client_id }` wire object solely to preserve the old shape.

## 5. Pairing token output is a bounded exception

An **approved pairing result** may legitimately contain the newly issued token long enough for the product caller to persist it in the secure credential store.

This is allowed:

~~~text
pairing finalize response
  → newly issued token
  → Keychain persistence
~~~

This is not allowed:

~~~text
saved token
  → every later Rust authority/grant request
~~~

Requirements:

- token appears only on the approved pairing result shape where required;
- non-approved statuses cannot carry it;
- Rust `Debug`/diagnostics for token-bearing DTOs must redact or omit it;
- tests must prove the token is absent from debug/error/trace output;
- 3-D will update Flutter to persist the token and stop resending it.

Do not remove the model-consent fields from the **saved server connection** itself; Inference still owns model-recipient consent. They simply do not belong in pairing/Access request DTOs.

## 6. Remote authority is Access intent, not model route intent

Post-pairing authority operations:

- inspect producer;
- review/enroll producer;
- enrollment status;

must use the current saved connection internally.

Conceptual flow:

~~~text
typed Remote Access service
  → CallerContext person/device
  → provider current authority transport
  → Access RemoteAuthorityStore / policy
~~~

No product request needs:

- base URL;
- bearer;
- `purpose`;
- `external`;
- `allow_external`;
- `recipient`;
- model route;
- connector catalog.

Provider adapters may add a store-backed `RemoteAuthorityEndpoint::from_current_connection(...)` or equivalent. App must not load the raw saved connection itself.

## 7. Remote grants are Access intent, not connection transport bundles

Post-pairing Calendar/View grant operations must speak in Access-owned source/reference/review terms.

Calendar:

- preview: connector, connection, resource;
- review: same + expected producer fingerprint;
- status/pause: grant identity + expected authority where required.

Remote view:

- preview: view, connector, connection, resource, consumer;
- review: same + exact expected producer/source/revision/provider/recipient facts;
- status/pause: grant identity + expected authority.

Transport/pairing identity is resolved from the current saved connection and validated against `CallerContext`.

`calendar_connections` must not be carried in a generic request. Source catalogs remain lazy observations via provider/Connections.

## 8. Typed App services define the final product boundary

Follow the 3-B Conversation service pattern.

Add narrow App service contracts for the product flows, conceptually:

~~~text
RemotePairingCommands
  prepare
  confirm
  status
  finalize

RemoteAccessCommands
  inspect producer
  review/enroll producer
  enrollment status
  calendar grant preview/review/status/pause
  view grant preview/review/status/pause
~~~

Exact names may differ if a cleaner existing naming convention emerges, but:

- every method accepts `&CallerContext`;
- caller identity is not duplicated in the request;
- App request values carry owner intent only;
- App delegates owner decisions to Connections/Access;
- secret-bearing transport preparation stays in provider adapters.

Do not make FFI call `VaultBridge`/`WorkerAction` directly for these final paths.

Internal Worker actions may carry the verified device ID supplied by the typed App service if required to execute asynchronously. That is trusted runtime context, not wire identity.

## 9. Protocol modules should reflect owner domains

Do not add another generic route-shaped file.

Prefer protocol organization such as:

~~~text
dto/connections.rs
  pairing setup/request/result values

dto/access.rs
  remote authority/grant request/result values
~~~

or an equivalent owner-oriented split.

The final DTO names should make it impossible to confuse:

- pairing endpoint;
- saved connection;
- model route;
- Access grant/source reference.

Keep `APP_WIRE_VERSION = 2` and `PROTOCOL_VERSION = 1` unless the checkout already differs for an unrelated committed reason.

Do not create `_v3`, `next`, legacy decoders or dual route formats.

## 10. FFI remains structural

New/final handlers may use dedicated typed FFI entry points or a clearly typed owner request surface. The exact ABI symbol naming can follow the repository's existing `_v2` convention.

Requirements are semantic, not cosmetic:

- one request envelope carries schema version + request ID + owner operation;
- handler calls `AppHost::request(request_id)`;
- operation converts to typed App service values;
- caller identity comes from `HostRequest::caller()`;
- FFI performs bounds/ID/enum/JSON conversion;
- FFI does not authorize grants, compare recipients, choose transport, load Keychain, or select models.

Update `crates/bindings/ffi/include/floe_ffi.h` in the same snapshot.

`floe_core_command_v2/query_v2/events_v2` remain canonical and unchanged.

## 11. Direct replacement, not dual contract preservation

The repository's refactor policy explicitly does not require old local API compatibility.

Therefore 3-C should directly remove the obsolete Rust route-shaped request contract once the final typed Rust contract exists.

It is acceptable and expected that, between 3-C and 3-D:

~~~text
Rust protocol/FFI = final contract
Flutter sender code = still old contract
~~~

3-D exists to close that caller mismatch.

Do **not** preserve `AgentRemoteRouteDto` or old remote AgentVault variants as aliases solely so old Flutter can continue to work for one checkpoint.

Flutter source itself is not modified in 3-C.
