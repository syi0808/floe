# 3-A — Remaining Root and Domain Caller Convergence

**Status: ready**

**Code baseline reviewed:** `39263a1339d0519b78a20680c0eea73506ff6d6f`

This document is the authoritative execution plan for 3-A.

## Goal

Move every live production model-execution caller intentionally left outside the Stage 2 General Conversation cutover onto canonical Inference ownership, while preserving each domain's own intent, prompt, budget and authorization semantics.

3-A does **not** redesign the Stage 2 runtime. It reuses it.

The production caller inventory on the reviewed baseline has three noncanonical clusters:

1. delegated built-in Expert model execution;
2. Schedule/Calendar model execution;
3. Knowledge Learner model execution.

A shared prerequisite is required before those callers can move: canonical Foundation prepared transport must reach the already-existing bundled native model.

## Frozen foundation

Do not reopen or replace these Stage 2 owners/invariants:

- Conversation Run/transcript/continuation/finalization;
- Agent Engine validated batches and durable pending side effects;
- exact Tool invocation identity and replay;
- delegation context digest and Task replay identity;
- TaskCoordinator admission, Task lifecycle, cancellation and single settlement;
- Conversation/Context model projection and dependency reauthorization;
- ContextToolService Tool reads and direct coverage;
- Inference profile observation, route/attempt/usage/fallback ownership;
- Access exact-recipient/current-authority/fence admission and post-response revalidation;
- parent-to-child cancellation direction;
- durable pre-dispatch intent and uncertain external-write recovery.

If a 3-A caller cannot use these contracts, adapt the caller or add the narrow owner-facing contract required by the caller. Do not recreate a parallel runtime.

## What is not 3-A

Do not in 3-A:

- redesign AppHost/FFI/Flutter contracts — 3-B through 3-D;
- delete `AgentRemoteRouteDto`, old FFI entry points or Flutter route maps — 3-C through 3-E;
- perform broad public-surface cleanup already closed in Stage 2;
- remove AgentFixture solely because it still uses legacy Conversation runtime — classify it for 3-D/3-E;
- rewrite pairing/grant product flows;
- create a second local-model implementation;
- change Stage 2 model dispatch or Access semantics just to fit a legacy caller.

## A0 — Canonical Foundation prepared transport

### Problem

`FoundationModelRunner` already uses the real bundled native path:

~~~text
FoundationModelRunner
  → foundation.rs native_call
  → floe_native::ByteCall
  → Frameworks/libfloe_local_model.dylib
  → floe_local_model
~~~

But canonical:

~~~text
InferenceService
  → FoundationModelProvider
  → PreparedFoundationTransport::generate
~~~

currently returns `AgentFailure::LocalModelUnavailable`.

Moving the 3-A callers first would therefore regress supported local execution.

### Required change

In `crates/adapters/providers/src/models/foundation.rs`:

- factor/reuse the existing private native request preparation and decode path;
- make `PreparedFoundationTransport::generate(CanonicalModelRequest)` invoke that same private native transport;
- preserve the canonical immutable envelope/catalog input;
- preserve Engine as output grammar owner;
- map the native response into `CanonicalModelResponse`;
- keep provider/native code free of Access/Context policy;
- keep deadline, cancellation, output bounds and protection semantics;
- do not expose native handles or raw prompt/provider internals through Inference public APIs.

Do not add a second dylib or a permanent `FoundationModelRunnerV2`.

### Focused proof

At minimum exercise:

- canonical Foundation provider observation;
- supported local generation;
- cancellation before dispatch;
- expired deadline;
- invalid/oversized native output mapping;
- unavailable native model maps to local model unavailable;
- existing legacy local-model smoke remains semantically equivalent until its callers are cut over.

3-D still owns final Apple packaging/build/product validation.

## A1 — Delegated built-in Expert model execution

### Target

~~~text
Manager Engine
  → DelegationPort / TaskCoordinator
  → durable Expert Task
  → Directory endpoint
  → Expert-owned prompt/context intent
  → canonical Inference execution
  → ExpertReport
  → TaskReceipt
  → Manager
~~~

### Required work

- introduce/use the narrow Expert model-execution dependency that delegates to canonical Inference;
- preserve Expert-specific prompt/role/schema validation in the Expert owner;
- preserve TaskId, InvocationKey, delegation context and Task settlement;
- source/context requirements must still flow through Context/Access rather than model placement;
- remove Expert-side Foundation/Server selection;
- remove Expert-side `candidate_route`, retry and usage ownership;
- remove `generate_with_recovery` use from the delegated Expert production path;
- preserve explicit profile behavior only if the Expert contract actually exposes such intent; do not synthesize provider route policy.

Do not replace `expert_compat.rs` with another compatibility wrapper carrying the same route/usage decisions.

### Closure proof

Production search after A1 should show no delegated Expert endpoint constructing:

- `FoundationModelRunner`;
- `ServerModelRunner`;
- `TransportModelRunner`;
- `ModelTransportRequest`;
- `candidate_route`;
- model usage/retry ownership parallel to Inference.

Tests/examples may retain old helpers only until later 3-A/3-E caller migration, with caller classification recorded.

## A2 — Schedule / Calendar execution

### Target

Schedule remains an Expert/domain owner for scheduling reasoning and capability semantics, but not a second model runtime.

Canonicalize the production endpoint behind `run_calendar_expert_endpoint` before deleting helper APIs.

Required changes:

- route Schedule model execution through the same Inference-owned execution contract established in A1;
- keep Schedule-specific Context views, Action proposal semantics and source requirements domain-owned;
- move direct source acquisition behind Context/Access owner ports where App/Schedule currently prepares provider clients directly;
- remove Schedule-owned model retry/usage accounting;
- remove `CalendarTurn` only after the endpoint no longer requires it;
- remove or reduce `run_calendar_agent_turn` only after its real caller count is zero;
- preserve Tool/capability durable identities and Action proposal/external-write recovery.

Do not replace the Schedule runtime with a copy of the General Conversation Engine unless the owner contract genuinely requires that abstraction. The requirement is common model/source ownership, not identical domain control flow.

## A3 — Knowledge Learner inference

### Target

~~~text
Knowledge Learner
  owns:
    eligible evidence
    learner prompt/input
    device-only / least-privilege policy
    deadline and domain budget
    candidate validation
          ↓
Inference
  owns:
    profile observation
    route
    attempt identity
    usage/settlement
    prepared transport
          ↓
Foundation prepared transport
~~~

Required changes:

- remove production `InferenceRouter::new` ownership from Knowledge;
- remove production construction of `ModelTransportRequest` from Knowledge;
- replace legacy `FoundationLearnerTransport`/raw `ModelTransport` execution with an Inference-owned request/service contract;
- keep the Learner device-only and isolated according to ADR 0019;
- preserve no-network/no-credential/no-domain-Tool constraints;
- preserve Learner-specific failure/defer behavior;
- make attempt identity and usage belong to Inference rather than Knowledge/App.

Do not let this change turn learning candidates into model-authoritative writes; the Review/candidate boundary is unrelated and remains frozen.

## A4 — Compatibility fallout and closure

After A0-A3:

- delete imports/private helpers/tests that exist only for the removed production paths;
- update focused tests to assert canonical owner behavior;
- do not perform unrelated AppHost/protocol cleanup;
- classify any remaining legacy runtime caller:
  - product domain caller still in 3-A;
  - fixture/product-boundary caller deferred to 3-D/3-E;
  - test/example only;
  - dead and safe to remove.

Expected production outcome:

- no delegated Expert/Schedule/Knowledge production code directly owns `ModelTransportRequest`;
- no delegated Expert/Schedule production code reconstructs Foundation/Server placement;
- no domain caller owns duplicate retry/usage settlement;
- Task/coverage/provenance/cancellation invariants remain unchanged.

## Acceptance

3-A is complete only when:

- canonical `PreparedFoundationTransport` can use the existing supported native Foundation transport;
- delegated built-in Experts use Inference-owned model execution;
- Schedule/Calendar has no parallel provider route/retry/usage owner;
- Knowledge Learner retains isolated domain policy while model execution is Inference-owned;
- no production 3-A caller constructs raw model route credentials or `ModelTransportRequest`;
- Expert Task identity, coverage/provenance and cancellation semantics are unchanged;
- remaining AgentFixture/product-wire compatibility is explicitly deferred to 3-D/3-E rather than used to keep 3-A runtime debt alive;
- focused and workspace checks are green;
- architecture checker reports zero errors/warnings;
- `git diff --check` is clean.

On completion:

1. mark this document `complete · frozen`;
2. check 3-A in `docs/refactoring/stage-3.md`;
3. move Current checkpoint to 3-B;
4. stop — do not implement 3-B in the same closure change unless its plan has been separately reviewed.
