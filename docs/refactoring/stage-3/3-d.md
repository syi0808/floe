# 3-D — Flutter, Native and Server Caller Cutover

**Status: pending · scope fixed from Stage 3 baseline review**

**Baseline used for scope:** `39263a1339d0519b78a20680c0eea73506ff6d6f`

## Goal

Move real Apple/Flutter/server callers onto the final 3-C product contracts and prove the canonical native/server adapters are packaged and reachable.

3-D consumes the contracts fixed in 3-C. It must not reintroduce route/policy decisions in Flutter or native code.

## D1 — Flutter Conversation

The current production Conversation runtime already uses:

~~~text
FloeClient
  → command_v2 conversation.start_turn
  → query_v2 / events_v2
~~~

Preserve this path.

Remove any remaining production fallback that performs a Conversation turn through AgentVault fixture/worker transport.

Explicit profile selection stays only as user/product intent. Flutter must not interpret profile IDs as local-versus-remote routing.

## D2 — Flutter connection/pairing/grant callers

Current `LocalServerClient.authorityRoute` and pairing/grant gateways build/pass maps containing endpoint and bearer plus model-route-shaped fields.

Migrate these callers to the 3-C Connections/Access intent contracts.

Requirements:

- no bearer bundle passed to Rust protected operations after credential persistence;
- no `purpose: everyday_assistance` or model-placement fields in pairing/grant commands merely to satisfy the old route DTO;
- preserve exact person/device/client/pairing identity;
- preserve reviewed producer/issuer/grant/source identity;
- presentation may display consent/review/recovery state but does not enforce authorization.

Direct Flutter→local-server management/pairing HTTP is not automatically forbidden. Remove only execution-policy coupling; keep genuine server management/connection behavior where it remains the product design.

## D3 — canonical native Foundation integration and Apple packaging

3-A0 makes `PreparedFoundationTransport` use the existing private native generation path.

3-D verifies the real Apple packaging/caller boundary:

- macOS/iOS build scripts still bundle `libfloe_local_model.dylib`;
- `floe_native::ByteCall` resolves the supported bundled library;
- FoundationModels availability/unavailability semantics are preserved;
- no Access/recipient/source policy moves into Swift;
- local model does not silently fall back to remote.

Do not create a second native model protocol.

## D4 — native source/secure-storage boundary

Keep OS-specific responsibilities in native/platform code:

- Keychain access;
- EventKit and other OS acquisition;
- native transport invocation;
- bounded host callbacks.

Preserve person/device/provider/scope/revision identity on observations.

Native callbacks do not decide:

- grant eligibility;
- model recipient;
- external-transfer consent;
- Context dependency authorization.

## D5 — server caller alignment

Server continues to own:

- pairing/authentication/OIDC/provider identity;
- provider credentials;
- model provider execution;
- connector/provider integration;
- capability/profile observation exposed by its API.

Preserve the separation:

~~~text
model profile discovery
!=
source connector discovery
~~~

Do not move local Access authorization to the server merely because it executes a provider request.

## D6 — AgentFixture disposition

AgentFixture is still a live Flutter/Rust compatibility path on the reviewed baseline.

Before 3-E, make one explicit product decision based on actual callers:

- if it is only synthetic/dev/validation behavior, remove it from production Flutter/runtime and keep equivalent fixtures in tests/examples/tools;
- if a real product surface still depends on its session/read behavior, migrate that surface to canonical Conversation/product services first.

Do not preserve a second production model runtime just to keep the fixture API unchanged.

## D7 — validation harness alignment

Repair stale Stage 3 validation entry points before using them as acceptance evidence:

1. `tools/validation/check-local-model.sh` references removed package `floe-infra`;
2. `apps/client/integration/local_server_pairing_test.dart` imports removed path
   `features/server/local_server_client.dart`.

Update them to the current owner/package paths as part of the relevant caller cutover. Do not replace the checks with weaker mocks.

## Focused validation

Expected coverage includes:

~~~sh
cargo build -p floe-ffi
cargo test -p floe-ffi

cd apps/client
flutter analyze
flutter test
flutter build macos
~~~

Also run the current local-model/native/server focused validation after repairing its entry points. iOS/device validation follows available Apple hardware/runtime and is recorded explicitly rather than inferred from macOS alone.

## Acceptance

3-D is complete when:

- Flutter Conversation uses only the final app command/query/event contract;
- Flutter protected Rust operations no longer construct internal endpoint/bearer/model route bundles;
- native code owns transport/OS/secure-storage mechanics, not Access policy;
- canonical prepared Foundation transport works from the packaged Apple build on supported conditions;
- server transport/provider code owns no local product authorization policy;
- source connector and model profile discovery remain separate;
- AgentFixture production disposition is resolved;
- stale validation harnesses required by 3-F are current;
- Apple client and Rust use one final protocol snapshot.

On completion, mark 3-D complete/frozen, update the Stage 3 checkpoint to 3-E and stop.
