# 3-D — Flutter, Native and Server Caller Cutover

**Status: ready**

**Execution baseline:** `b63b5c1fd76afbb7f28ab02c6f0d84dc2070db10` (`docs: freeze Stage 3-C and hand off caller cutover to 3-D`)

This document is the authoritative execution plan for 3-D.

Read the frozen 3-C handoff first:

- `docs/refactoring/stage-3/3-c.md`
- especially its Agent report item **11 — Exact unchanged Flutter 3-D handoff**

## Goal

Move the **real product callers** onto the Rust protocol/FFI contracts frozen by 3-C and prove that the Apple-native/server delivery boundary actually packages and reaches those contracts.

3-D is caller cutover, not another Rust contract redesign.

After 3-D:

- Flutter remote pairing uses `floe_core_remote_pairing_v2`;
- Flutter remote authority/Calendar/View grant calls use `floe_core_remote_access_v2`;
- Flutter sends pairing setup intent, never the old route bundle;
- Flutter sends no saved bearer/endpoint to protected Rust Access operations;
- approved pairing credentials are persisted before the bounded Rust result is released;
- the dead `authorityRoute()` / `pairingRoute()` request builders are gone;
- the unimplemented `PairingOperationGateway` split is gone; one production pairing gateway owns submit/read-result/release;
- canonical Conversation remains `command_v2/query_v2/events_v2`;
- synthetic AgentFixture transport is no longer part of the production Flutter assistant path;
- shared Conversation session/message view models no longer live under a fixture-named production API;
- macOS and iOS packaging still include the Rust FFI and canonical local-model dylibs from one source snapshot;
- stale local-model and local-server validation entry points are repaired;
- server pairing/authorization/provider semantics are verified against the new client caller path without moving local Access policy to Go.

3-E owns final Rust/FFI caller-zero compatibility deletion after this caller cutover.

# Fixed 3-D design

## 1. One production native transport, owner-specific request methods

`NativeTransport` remains the app-lifetime FFI transport.

Add final owner methods conceptually:

~~~text
remotePairingV2(request)
remoteAccessV2(request)
~~~

They use the same schema-2 App response-envelope validation already used by:

~~~text
commandV2
queryV2
eventsV2
~~~

The native isolate dispatches:

~~~text
remote_pairing_v2 → floe_core_remote_pairing_v2
remote_access_v2  → floe_core_remote_access_v2
~~~

Do not route these requests through `agent_vault`.

Do not reimplement request correlation separately if the existing schema-2 helper can be shared safely.

## 2. Flutter remote gateways are owner-shaped

Do not keep remote pairing/access methods on a generic map-shaped route API.

Preferred production split:

~~~text
RemotePairingGateway
  → pairing owner transport

RemoteAccessGateway
  → Access owner transport

NativeAgentVaultGateway
  → unrelated old AgentVault operations still live until 3-E
  → ConversationSession / Registry / Memory / etc.
~~~

Exact Dart class names can differ, but product code must make it impossible to accidentally pass:

- `bearer_token`;
- model `purpose`;
- `external` / `allow_external`;
- model recipient;
- `calendar_connections`;
- caller-supplied person/device;
- generic `route`.

No new `Map<String,Object?> route` parameter may replace the old one under another name.

## 3. Pairing lifecycle belongs to one production gateway

The reviewed baseline has:

~~~text
RemotePairingGateway
PairingOperationGateway
~~~

but **no production implementation of `PairingOperationGateway`**.

`SettingsScreen` passes only `pairingGateway`, so `LocalServerPanel._drive()` exits when `pairingOperations == null`.

Do not implement this stale split.

Converge pairing lifecycle into one production pairing gateway backed by the 3-C Rust owner API:

~~~text
prepare
confirm
status/read-result
finalize
release
~~~

Delete `PairingOperationGateway` if caller-zero after the panel migration.

### Pairing operation lifecycle

Rust remote owner jobs are asynchronous and use:

~~~text
submit operation
→ bounded read_result(operation_id)
→ release completed result
~~~

Flutter should centralize this lifecycle in one helper.

Rules:

- submit exactly once per operation ID;
- poll with bounded cadence/deadline;
- do not use AgentVault poll/stop/release;
- a read timeout is not implicit cancellation;
- validate response `operation_id`;
- owner failure becomes a typed Flutter failure;
- do not rewrite owner failure/recovery metadata.

### Approved-token release rule

For pairing finalization:

~~~text
Rust result with Approved { client_id, token }
→ Flutter validates exact pairing/person/device
→ persist ServerConnection to Keychain
→ verify saved identity
→ release Rust result
~~~

Do **not** release the completed result before persistence succeeds.

If persistence fails:

- do not pretend pairing is connected;
- retain enough bounded operation identity to retry/read according to the Rust contract;
- never print/log the token;
- do not create a second server credential.

Other non-secret pairing results may be released after successful decode/acceptance.

## 4. Direct server pairing setup remains connection intent

Flutter still directly calls the local server for the initial `/pair/start` setup because the server must issue:

- pairing ID;
- polling proof;
- comparison code;
- producer identity;
- signed challenge.

This remains valid connection setup.

Keep strict setup:

~~~text
LocalServerClient.startPairingStrict(...)
~~~

with:

- person/device exact match to local identity;
- owner issuer key from Rust `Prepare`;
- loopback-only endpoint;
- no bearer;
- no model route.

After the challenge exists, confirm/status/finalize go through Rust Connections via the final pairing FFI contract.

Direct `/pair/cancel` may remain as bounded server setup cleanup because the 3-C owner contract has no cancel operation. It must use the exact pairing ID/proof and must not be confused with Run cancellation.

## 5. Saved connection is not a request route

Keep `ServerConnection` / Keychain persistence because it owns:

- server address;
- issued bearer;
- client ID;
- person/device binding;
- model external-transfer consent state.

Remove its use as a Rust request bundle.

Delete production:

~~~text
LocalServerClient.authorityRoute(...)
LocalServerClient.pairingRoute(...)
~~~

after callers migrate.

The bearer remains:

~~~text
Flutter pairing result
→ Keychain
→ Rust CurrentSavedConnectionStore
```

not:

~~~text
Flutter pairing result
→ Keychain
→ read back
→ resend as Rust request
~~~

Flutter may continue using the saved credential for genuine **server-management/Connections UI HTTP** where that is the product design, such as connector catalog/connect/disconnect/scope management.

That direct management path must not be repurposed to execute Rust model/Access policy.

## 6. Remote Access caller identity is implicit

Final Flutter `RemoteAccessGateway` methods do not take `personId` as authority.

Examples:

~~~text
inspectRemoteProducer()

reviewAndEnrollRemoteProducer(producer)

remoteEnrollmentStatus(enrollmentId)

previewRemoteCalendarGrant(
  connectorId,
  connectionId,
  resource
)

reviewRemoteViewGrant(
  viewId,
  connectorId,
  connectionId,
  resource,
  consumer,
  expectedProducerFingerprint,
  expectedSourceAuthority,
  expectedConnectionRevision,
  expectedProviderIdentity,
  expectedRecipient
)
~~~

`CallerContext` comes from AppHost.

Flutter may compare returned person/source/connection values for UI stale-result rejection, but it does not supply trusted identity to Rust.

## 7. Access result polling may release after acceptance

Unlike the approved pairing credential, remote Access results contain no newly issued secret that Flutter must first persist.

The gateway may:

~~~text
submit
→ poll read_result
→ validate/decode owner result
→ release
→ return product value
~~~

Preserve:

- operation ID correlation;
- result ownership;
- exact review expectation fields;
- grant authority;
- connection revision;
- producer/source/provider/recipient identity;
- failure envelope semantics.

A failed release acknowledgement is not permission to resubmit a mutation with a new operation ID.

Use the same operation ID to reconcile according to the final contract.

## 8. Production Conversation has no synthetic fixture fallback

The real assistant already uses:

~~~text
AgentConversationGateway
+ ConversationRuntimeProvider
+ NativeConversationRuntimeGateway
→ command_v2/query_v2/events_v2
~~~

Keep this as the only production conversation-turn path.

The reviewed Flutter type graph still makes:

~~~text
AgentVaultGateway implements AgentFixtureStreamingGateway
AgentController requires AgentFixtureStreamingGateway
```

and contains synthetic fallback branches.

That production coupling must end in 3-D.

### Required disposition

Synthetic AgentFixture is **dev/test tooling**, not a second product assistant runtime.

Therefore:

- remove dead `AgentFixtureFacade` construction from `main.dart`;
- remove unused `FloeApp.agentFixture`;
- production `NativeAgentVaultGateway` must no longer implement synthetic fixture run APIs;
- production `NativeTransport` must no longer need `agent_fixture` / `agent_fixture_run` dispatch for the app;
- `AgentController` product path must depend on a product gateway boundary that supports vault lifecycle + Conversation + the actual registry/memory/connections/etc. capabilities, not on `AgentFixtureStreamingGateway`;
- remove fixture fallback branches from the production controller;
- preserve canonical Conversation start/resume/recover/send/cancel semantics.

### Shared model types

`AgentSession`, `AgentMessage`, `AgentContinuation`, `AgentOutcome` and related values are also used by canonical Conversation.

Do not delete them merely because they currently live in:

~~~text
agent_fixture_gateway.dart
~~~

Move/shared-export them under an owner-neutral Conversation/session model location first.

Tests may keep explicit synthetic fixture gateways under `test/support` or a clearly non-product dev tool.

### Rust fixture deletion boundary

3-D proves Flutter production caller count zero for:

~~~text
floe_core_agent_fixture
floe_core_agent_fixture_run
AgentFixture runtime
```

but does **not** have to delete the Rust ABI/runtime in the same slice.

3-E owns caller-zero Rust/protocol/App deletion after this proof.

Do not keep production Flutter fixture bindings solely so Rust remains reachable.

## 9. Apple local model packaging is one canonical path

Do not alter the native model protocol from 3-A.

The real packaging path must remain:

~~~text

→ floe_native::ByteCall
→ Frameworks/libfloe_local_model.dylib
→ LocalModel.swift
→ FoundationModels
```

### macOS

`apps/client/macos/build_rust.sh` must continue to:

- build `floe-ffi`;
- copy/sign `libfloe_ffi.dylib`;
- compile/sign `libfloe_local_model.dylib`;
- place both in app Frameworks;
- retain the required install name.

### iOS/iPadOS

`apps/client/ios/build_rust.sh` must continue to:

- build Rust for selected device/simulator architectures;
- compile LocalModel Swift for the corresponding architecture;
- weak-link FoundationModels;
- lipo when required;
- sign and place `libfloe_local_model.dylib` in Frameworks.

Do not infer physical-device FoundationModels availability from a simulator build.

## 10. Native/platform code remains mechanical

Native/platform code owns:

- FFI symbol lookup;
- dylib loading;
- Keychain storage bridge;
- EventKit/Contacts/Screen Time/Health acquisition;
- bounded native callbacks;
- FoundationModels invocation.

It does not own:

- Access grant eligibility;
- exact model recipient consent;
- Context dependency authorization;
- Expert eligibility;
- Inference fallback;
- model/source discovery coupling.

No Stage 3-D change may move policy into Swift to simplify Dart/Rust wiring.

## 11. Server remains the remote producer/provider, not local authority

3-D verifies the final client path against existing Go server semantics.

Server continues to own:

- pairing HTTP protocol;
- local dashboard approval;
- paired client credentials;
- OIDC/provider credentials;
- connector integrations;
- provider model execution;
- remote producer/source descriptors.

Rust client still owns local Connections/Access decisions.

Do not redesign server endpoints merely because Flutter changes its caller path.

Expected compatible server wire remains:

~~~text
/pair/start
/pair/confirm
/pair/poll
/v1/authority/...
/v1/views/...
/v1/connectors/...
```

Any required server change must be justified by a concrete mismatch between the frozen 3-C adapter and server protocol, not by product-layer convenience.

## 12. Validation harness must become current before 3-D closes

Known stale entries are part of 3-D, not deferred again.

### Local model harness

`tools/validation/check-local-model.sh` currently ends with:

~~~text
cargo test -p floe-infra --lib local_model
```

where `floe-infra` no longer exists.

Replace this with current canonical validation, retaining or increasing coverage.

At minimum:

- Swift `LocalModelHostTests.swift`;
- canonical provider-adapter Foundation tests;
- canonical Inference tests if the script claims Rust model-path validation.

Do not replace the host tests with a lighter grep/smoke.

### Local server pairing integration

`apps/client/integration/local_server_pairing_test.dart` imports the removed:

~~~text
features/server/local_server_client.dart
```

Update it to the current Connections path.

Also classify its semantics:

- if it remains a direct Go server pairing/credential smoke, update it to the **current strict pairing protocol** and name it honestly;
- if it claims to validate the app's final Rust pairing contract, route pairing through the new native owner gateway instead of manually reproducing old `/pair/poll` semantics.

Do not leave a green test that exercises an obsolete pairing protocol.

3-F may add broader live-product evidence; 3-D must at least leave all validation entry points truthful and runnable.
