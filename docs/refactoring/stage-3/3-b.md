# 3-B — AppHost Composition Closure

**Status: ready**

**Execution baseline:** `04b23e06dc1219ad43b7eab1781d118202a4af7e` (`refactor: close Stage 3-A Schedule runtime residual`)

This document is the authoritative execution plan for 3-B.

## Goal

Make App/AppHost a **construction, lifecycle, caller-admission and typed owner-service routing boundary only**.

After 3-B:

- product turn requests carry turn intent, never a credential source;
- one host-scoped current-connection dependency is injected into the Vault/Conversation runtime;
- provider adapters load/admit credentials internally and expose only opaque prepared capabilities or non-secret observations to App;
- App does not inspect model profiles to decide Expert eligibility;
- App does not couple remote source availability to model-profile availability;
- General Conversation, built-in Expert and Schedule execution receive owner services/concrete adapters through composition rather than reconstructing secret-bearing topology in each runtime entry;
- canonical AppWire command/query/events use typed AppHost service traits and do not reach through `AppComposition` into `VaultBridge` or `AppEventBuffer`;
- old FFI/AgentVault compatibility may remain only where 3-C/3-D still has a live caller.

3-B does **not** redesign the Stage 2/3-A canonical runtime. It closes the composition seams around it.

## Frozen foundation

Do not reopen or weaken:

- Stage 2 Conversation Run/transcript/continuation/finalization;
- Engine validated batches, cursor replay and durable side-effect identity;
- Context projection, provenance, coverage, freshness and history reauthorization;
- ContextToolService Tool semantics;
- Inference profile selection, attempt identity, retry/fallback and usage settlement;

- 3-A `InferenceExecutor` / `InferenceExecutionConstraint`;

- Schedule's single canonical Expert endpoint;
- Knowledge Learner isolation and canonical Inference execution;
- Action approval/external-write uncertainty;
- Connections pairing/OIDC/server identity.

If composition needs a new port, add the narrow owner-facing port required to express construction or non-secret observation. Do not move owner judgment into App.

# Fixed 3-B design

## 1. What App may and may not do

App **may**:

- construct concrete repositories/adapters;
- construct owner services;
- bind verified person/device identity to those concrete dependencies;
- hold host-scoped stores and platform brokers;
- choose which concrete implementation satisfies an owner-defined port;
- manage worker/runtime lifetime and shutdown;
- translate owner failures into App service failures;
- pass owner-produced non-secret observations between owners when the receiving owner defines the meaning.

App **must not**:

- read a saved model/server credential merely to decide product/domain behavior;
- materialize `SavedServerConnection` in turn/Expert/Schedule execution code;
- choose Foundation versus Server;
- inspect `ModelProfile.execution_location` / `data_recipient` to decide Expert eligibility;
- infer source availability from model-profile availability;
- decide recipient consent or grant authority;
- decide whether a remote source is authorized;
- duplicate Inference retry/usage logic;
- pre-resolve a model or source route.

A `floe_provider_adapters` import is not itself a violation. **Construction is allowed; interpretation is not.**

## 2. One host-scoped current-connection dependency

Today the same host keychain concept appears in two App-owned forms:

~~~text
ConversationTurnRequest::SavedConnectionSource
EndpointConnectionStore
~~~

while provider adapters already expose `SavedConnectionStore` implementations such as `SavedServerConnectionStore` / `CurrentSavedConnectionStore`.

3-B must converge this to **one injected current-connection store/factory at the host/VaultBridge/Worker lifetime**, shared by:

- General Conversation root model/source wiring;
- built-in Expert endpoints;
- Schedule endpoint;
- exact-recipient authority.

Tests inject a fixed current store at the host/worker construction boundary, not into a turn request.

Prefer reusing the provider/inference-owned saved-connection store abstraction. Exact concrete naming may change, but do not create a third App-specific credential enum.

## 3. Provider adapters own credential loading/admission

App runtime code must not call:

- `load_saved_connection`;
- `SavedConnectionStore::load` to obtain a raw connection;
- `PreparedServerSource::admit` on a raw connection;
- `RootModelProvider::for_saved_connection*` with a raw saved value;
- `ServerSourceClient::prepare` with a raw saved value.

Add/reuse store-backed provider-adapter construction so the adapter loads and admits the current connection internally.

Acceptable semantic shape:

~~~text
host-scoped CurrentConnectionStore
          │
          ├─ provider-owned current model factory
          │    → opaque RootModelProvider / prepared transports
          │
          ├─ provider-owned current source factory
          │    → opaque optional Server source capability
          │
          └─ SavedConnectionRecipientAuthority
               → re-load current connection at every recipient check
~~~

Exact type names may differ. The key requirements are:

- raw endpoint/token remain inside provider/control adapters;
- verified person/device identity is passed into adapter preparation;
- malformed/foreign saved identity fails closed;
- no secret enters `ConversationTurnRequest`, Context projection, Expert invocation or protocol;
- recipient authority still re-reads current state at the existing fence points.

A model/source adapter may be created per operation if required for bounded lifetime. The **store/factory is host-scoped**; the secret is not request-scoped.

## 4. Model availability and source availability stay separate

3-A intentionally separated source discovery from model profile discovery. 3-B must not rebuild that coupling in App.

Current built-in Expert endpoint code observes model profiles and derives:

~~~text
has_device_model
has_remote_model
server_source_allowed
~~~

with `server_source_allowed` partly derived from Gateway model availability.

This must change.

- Inference owns "can this purpose/consumer execute under DeviceOnly / RemoteOnly / Any?"
- Experts owns "which cards are eligible for the execution classes available?"
- Context/Connections/provider source boundary owns "is a paired remote source capability available?"
- App wires those owner outputs together; it does not inspect raw profile fields.

A narrow Inference non-secret availability API is acceptable, for example a `can_execute(constraint)`/availability observation backed by the same provider facts. It must not expose credentials or ask App to reproduce candidate ranking.

A narrow Experts availability helper/value is acceptable. Do not make App implement Expert placement policy by hand.

`server_source_allowed` must not survive as "source is usable because a Gateway model exists."

## 5. Source acquisition stays behind owner ports

General Conversation, built-in Experts and Schedule currently call provider source constructors in App runtime modules.

The final shape is:

~~~text
Context / Expert / Schedule owner
  → asks for source/view capability in owner terms
  → Access/grant/current-authority checks
  → injected source adapter/factory
  → provider transport
~~~

App can construct/inject the concrete source adapter or factory. App runtime endpoints must not interpret connection credentials or connector catalogs to decide authorization.

For Schedule specifically:

- `schedule::plan_run` may continue to decide that Google/Microsoft acquisition is remote and that freshly remote-acquired data requires on-device reasoning;
- the input should mean **remote source capability available**, not "remote model route available";
- `ScheduleEndpoint` must no longer reach directly through a credential to create/inspect a provider source route;
- connector enumeration remains lazy and source-specific;
- model profile observation remains completely separate.

Do not move Schedule reasoning into App.

## 6. Typed canonical AppHost services

`ConversationCommands` is already the correct pattern.

3-B adds equivalent typed App service surfaces for canonical AppWire query/events, so the canonical binding path becomes:

~~~text
HostRequest
  → ConversationCommands
  → ConversationQueries
  → ConversationEvents
~~~

and never:

~~~text
HostRequest
  → AppComposition
  → agent_vault()
  → conversation_query()/app_events()
~~~

The exact request/result names may vary, but service contracts must:

- accept `CallerContext`, not a caller-supplied person/device override;
- expose Conversation run/command/message read intent;
- expose bounded event cursor/read intent;
- return App/owner values, not `VaultBridge`, `AppEventBuffer` or worker internals;
- keep AppWire schema/DTO semantics unchanged in 3-B.

`AppComposition` implements the service traits by delegating to the existing worker/event machinery.

FFI AppWire performs DTO ↔ App-service-value conversion only.

## 7. Outer compatibility is caller-based

3-B does **not** delete live old ABI just because canonical AppHost no longer needs it.

Expected temporary live compatibility after 3-B may include:

- `FloeHandle::services()` → `AppHost::legacy_services()`;
- `AppHost::legacy(...)`;
- old AgentVault ABI;
- old Day/local-context/action APIs that still call `AppComposition` getters;
- `agent_run::run` / AgentFixture;
- protocol/Flutter route DTOs owned by 3-C/3-D.

However:

- canonical `app_wire.rs` command/query/events must have zero dependency on `legacy_services()`, concrete `AppComposition`, `VaultBridge` or `AppEventBuffer`;
- tests for canonical AppWire must not use `legacy_services()` merely to inspect captures;
- any public App type/module made caller-zero by that migration should be minimized now if it is direct 3-B fallout and no later outer caller uses it.

Do not begin 3-C DTO migration.
