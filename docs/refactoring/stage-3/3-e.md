# 3-E — Outer Compatibility Deletion

**Status: active — E7 final validation**

**Execution baseline:** e54f31e49ebfa38ab14d8a1a98b1ce13ce5fa2ab (docs: freeze Stage 3-D residual closure and activate 3-E)

**Actual execution baseline:** `575dc0013db08c5efa2a27a2f189e19041904ba4`, identical to freshly fetched `origin/main` on 2026-09-22. The initial worktree was clean; the planned baseline is an ancestor. One coding agent, existing `main`, no parallel agent work.

This document is the authoritative execution plan for 3-E.

3-A through 3-D are complete · frozen. 3-E does not redesign their runtime. It removes the remaining outer compatibility by first moving every still-live product caller to verified, owner-shaped AppHost services and then deleting the now caller-zero ABI/runtime surface.

The earlier Stage 3 baseline deletion list is historical. Current source decides what is live.

## Goal

End Stage 3-E with one outer product architecture:

~~~text
Flutter / native caller
  → final typed product protocol
  → admitted AppHost request
  → verified CallerContext
  → typed owner service
  → canonical owner/runtime
  → adapter
~~~

The local Rust C ABI should converge to this set unless exact caller proof finds an unavoidable owner-specific exception:


Delete, rather than rename, the old generic/product-compatibility paths after their callers migrate:

~~~text

floe_core_load_day
~~~

# Fixed 3-E product-boundary design

## 1. Reuse the final local AppWire

For local product commands/queries, extend the already canonical:

~~~text
floe_core_command_v2
floe_core_query_v2
~~~

with owner-prefixed typed DTO variants.

Do not create:

- command_v3/query_v3;
- agent_vault_v2;
- product_v2 catch-all;
- a new generic Map action bus;
- a wire enum mirroring WorkerAction or WorkerOperation.

The wire states owner intent. App converts it to private worker/service machinery.

events_v2 remains Conversation event delivery unless a real current product caller proves an additional event domain is required.

## 2. Identity is never a product argument

Every new local owner command/query must enter through:

~~~text
AppHost::request(request_id)
→ CallerContext
→ typed service
~~~

Remove trusted person_id/device_id from the migrated product request shapes.

Domain fields such as a reviewed connection ID, source authority, calendar ID, session ID, registry revision or grant expectation remain when they are genuine owner intent.

If a request refers to the current device, the service derives it from CallerContext. Flutter may compare returned identity for stale-result rejection; it does not supply authority.

## 3. Preserve non-blocking owner jobs without exposing WorkerOperation

Some Vault/Access/Expert operations must allow the FFI isolate to return while native acquisition or other work continues.

For those operations:

- command_v2 submits the typed owner command with stable command/operation identity;
- query_v2 observes the matching typed owner result and may release it after accepted decode;
- product DTOs must not expose generic submit/poll/stop/release WorkerOperation JSON;
- App may use VaultBridge/WorkerOperation privately;
- query/preview/read timeouts are not implicit Run/Task cancellation;
- an uncertain submit/read/release acknowledgement reuses the same owner operation identity.

A small shared AppWire operation-correlation helper is allowed only if it handles envelope/operation identity mechanically. It must not accept arbitrary WorkerAction maps or interpret domain policy.

## 4. Owner services are explicit

Add/extend typed App service traits rather than letting FFI read AppComposition internals.

Expected service ownership:

~~~text
VaultLifecycleCommands / Queries
ConversationSessionCommands / Queries
ExpertCommands / Queries
LocalAccessCommands / Queries
KnowledgeCommands / Queries
ConnectionsQueries
ActionCommands / Queries
DayCommands / Queries
LocalContextCommands / Queries
~~~

Exact Rust trait names may be shorter, but each API must be owner-shaped and require CallerContext.

FFI performs only:

~~~text
strict DTO validation
→ AppHost admission
→ DTO ↔ owner value conversion
→ result/error serialization
~~~

No FFI credential loading, authorization policy, model routing, registry eligibility or Action decision policy.
