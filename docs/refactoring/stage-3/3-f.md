# 3-F — End-to-End Product Validation

**Status: pending · final gate scope fixed from Stage 3 baseline review**

## Goal

Validate the final Stage 3 product from one recorded source snapshot across the canonical Rust runtime and real Apple/product boundaries.

Mock-only green tests are insufficient for this final gate. Existing fixture tests remain necessary, but platform/provider claims require the corresponding real controlled evidence.

## Precondition

3-A through 3-E must be complete/frozen.

Before collecting evidence, confirm the Stage 3 validation harness is current. The baseline review already found two stale entry points that must be repaired by 3-D or at the start of 3-F:

- `tools/validation/check-local-model.sh` references removed package `floe-infra`;
- `apps/client/integration/local_server_pairing_test.dart` imports removed
  `features/server/local_server_client.dart`.

Do not mark 3-F green while required validation commands point at removed code.

## Source/environment record

Record with the final evidence:

- exact Git commit;
- Rust toolchain;
- Flutter/Dart version;
- Xcode/SDK/runtime version;
- macOS version and Apple hardware/model-availability condition;
- server binary/source commit used;
- whether each provider/OAuth/native-source check was real, fixture or unavailable;
- disposable test account/calendar/source identifiers where applicable without recording secrets.

## General Conversation

Validate:

- Flutter → FFI → AppHost admission → Conversation → Engine → Inference → Access → prepared Provider → reply;
- Auto profile behavior;
- explicit profile behavior where the UI/product exposes it;
- supported local Foundation path;
- approved remote model path when configured;
- no remote fallback for unavailable local-only explicit profile;
- final answer/message projection;
- restart/reload/read-model resynchronization.

## Tool/source use

Validate:

- Manager ToolCall → ContextToolService;
- authorized local source read and exact direct coverage;
- authorized remote source read where configured;
- denied/revoked/unavailable source fails closed or degrades according to the owner contract;
- next model call sees the exact ToolExchange;
- source connector discovery is not used as model profile routing input;
- dependency reauthorization rejects stale/revoked history.

## Expert delegation

Validate:

- Manager → durable Expert Task → Directory endpoint → Expert execution → TaskReceipt → Manager;
- stable TaskId/InvocationKey on replay;
- delegation context digest/binding;
- Schedule/built-in Context and Access behavior;
- cancellation direction;
- denied/revoked Task semantics;
- no duplicate Expert settlement;
- no domain-local model route/retry/usage owner reappears.

## Knowledge Learner

Validate at least one controlled eligible completed turn:

- foreground turn completion is not blocked by Learner execution;
- Learner uses isolated budget/cancellation/policy;
- model execution flows through canonical Inference;
- no credential/network/domain Tool access is granted to Learner;
- candidate is staged/reviewed rather than directly activating knowledge;
- retry/restart does not duplicate the candidate.

## Security / model recipient

Validate:

- exact current recipient is required;
- unconsented external recipient prevents provider handoff;
- revocation before handoff results in provider calls = 0;
- revocation during/after model call suppresses unauthorized release while usage/attempt settlement remains correct;
- saved credential identity must match current person/device;
- no raw bearer/token appears in FFI/Flutter requests, responses or diagnostics;
- provider Debug/serialization remains redacted.

## Durable recovery / replay

Validate Stage 2 invariants from the final product boundary:

- crash/restart after validated batch persistence;
- crash/restart after Tool result before cursor;
- crash/restart after Delegation result before cursor;
- cross-run continuation takeover;
- retry of same command/request identity;
- no duplicate external effect;
- no lost pending batch;
- no model re-plan where durable plan already exists;
- cancellation cannot resurrect budget or child execution.

## Actions / uncertain external write

Use the existing controlled S3 Calendar validation assets where applicable:

- fixture ABI end-to-end;
- approved proposal → dispatch;
- exact proposal/execution marker;
- response-loss/unknown external-write recovery;
- no duplicate Calendar create on recovery;
- cleanup verifies only the exact disposable event;
- no TCC/database manipulation to force a pass.

Follow `tools/s3-validation/README.md`; do not ship its fault-injection shim.

## Apple native evidence

Validate supported macOS product flow:

- app/FFI dylib loads;
- local identity and encrypted Vault open/reopen;
- Keychain saved server connection read/write path;
- bundled `libfloe_local_model.dylib` availability and one controlled generation when supported;
- EventKit/source permission/read behavior relevant to the product flow;
- permission denial/revocation remains recoverable and fail-closed;
- app shutdown does not leave an active Run/Vault owner incorrectly held.

For iPhone/iPad, run the supported smoke/build/device checks available to the environment and record what was actually exercised. Do not claim device evidence from a compile-only build.

## Server/provider evidence

Where configured:

- local server pairing with exact person/device identity;
- issued credential persistence;
- current connection authorization;
- pairing/producer/issuer identity pinning;
- provider/OAuth connector path relevant to the tested source;
- model purpose/profile observation;
- connector catalog remains a separate source concern;
- credential deletion/revocation blocks later protected use.

If a real external provider is not configured, record it as not exercised; do not substitute a mock and label it real-provider acceptance.

## Automated closure

Run, at minimum, the final repository gates:

~~~sh
cargo check --workspace --lib
cargo test --workspace --no-fail-fast
python3 tools/architecture/check_boundaries.py
git diff --check
~~~

And Apple/Flutter gates from the same source snapshot:

~~~sh
cargo build -p floe-ffi

cd apps/client
flutter analyze
flutter test
flutter build macos
~~~

Run the repaired local-model/native/server focused scripts and any controlled S3 Calendar validation required for the claims being closed.

## Final acceptance

Stage 3 is complete only when:

- all 3-A through 3-E caller/compatibility gates remain closed under the final product build;
- General Conversation, Tool and Expert paths execute through canonical owners;
- Knowledge Learner no longer owns raw model transport execution;
- raw product-wire model credentials/topology are absent;
- canonical Foundation native path works under supported Apple conditions;
- exact-recipient/revocation/recovery invariants pass;
- controlled uncertain external-write recovery passes;
- real Apple/platform/provider evidence is recorded for every claimed supported path;
- full Rust/Flutter/architecture/diff gates are green;
- no known stale validation harness remains in the final acceptance set.

When complete, mark 3-F and Stage 3 complete/frozen and update active refactoring guidance only if a new stage actually exists. Do not invent a Stage 4 solely as a cleanup bucket.
